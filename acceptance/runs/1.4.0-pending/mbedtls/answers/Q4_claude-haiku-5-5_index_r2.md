The negative code becomes a string through `mbedtls_strerror()` in `library/error.c`. The string tables are generated, so a contributor adds a code by editing the module header and regenerating, not by hand-editing `error.c`.

**Runtime path**

```
caller: mbedtls_strerror(ret, buf, buflen)            library/error.c:792
  ├─ buflen == 0 → return; memset(buf, 0, buflen)
  ├─ ret < 0 → ret = -ret                             (codes are negative; tables store positive values)
  ├─ ret & 0xFF80 → high part
  │     mbedtls_high_level_strerr(ret)                 error.c:174  switch on ret & 0xFF80
  │       NULL → "UNKNOWN ERROR CODE (%04X)"
  │       SSL fatal alert (use_ret == 0x7000-ish) → return early, skip low part
  ├─ use_ret = ret & ~0xFF80; 0 → return
  ├─ buf already non-empty → append " : "
  └─ mbedtls_low_level_strerr(ret)                     error.c:537  switch on ret & ~0xFF80
          NULL → "UNKNOWN ERROR CODE (%04X)"
```

So `-0x6080`-style values produce `CIPHER - …`, and a combined code such as a high-level module code plus a low-level code produces `"HIGH - desc : LOW - desc"`. The buffer is always null-terminated. When `MBEDTLS_ERROR_C` is off, a dummy version at `error.c:144` just writes an empty string.

**Where the tables come from**

- Each error is a `#define MBEDTLS_ERR_<MOD>_<NAME> -0x00XX` in a public header under `include/mbedtls/` (e.g. `aes.h:50`). The bit layout is documented at the top of `include/mbedtls/error.h:17-91`.
- `scripts/generate_errors.pl` scans `include/mbedtls/*.h` for those defines. The description comes from the Doxygen comment, either before the define (`/** … */`) or after it (`/*!< … */`). It dies if a define has no description, has both, or duplicates a value.
- It classifies each module as low-level (`@low_level_modules`) or high-level (`@high_level_modules`) and emits `case -(NAME): return("MOD - description");` into the switch blocks of `error.c`, guarded by `#if defined(MBEDTLS_<MOD>_C)`.
- `scripts/data_files/error.fmt` is the template. The generator replaces the `HEADER_INCLUDED`, `LOW_LEVEL_CODE_CHECKS` and `HIGH_LEVEL_CODE_CHECKS` placeholders.
- `library/error.c` is regenerated by `library/Makefile:355-360` (`perl ../scripts/generate_errors.pl`) and by `library/CMakeLists.txt:139-146`. `tests/scripts/check-generated-files.sh:135` fails CI if the checked-in `error.c` differs from the generator's output.

**What a contributor does to add one**

1. Pick a code in the module's range from the `error.h` table. Check that it does not already appear in another header, since the generator rejects duplicates.
2. Add `#define MBEDTLS_ERR_<MOD>_<NAME> -0x00XX` in that module's header, with exactly one Doxygen description, before or after, not both.
3. If the module is new, add it to `@low_level_modules` or `@high_level_modules` in `scripts/generate_errors.pl`. Otherwise the generator exits with "Do not know how to handle". Its module-to-header-name mapping has special cases (`NET` → `net_sockets`, `MPI` → `BIGNUM`), so a new module whose header name does not match the lowercased module name needs one too, or the "has not been included" check fails.
4. Regenerate with `make -C library error.c` (or a CMake build). Do not edit the auto-generated section of `library/error.c` by hand.
5. Commit both the header and the regenerated `error.c`. CI's generated-file check will reject a stale `error.c`.
