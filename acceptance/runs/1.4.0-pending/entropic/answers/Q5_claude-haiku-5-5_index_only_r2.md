**Short answer:** Python never links against the C++ code. It loads `librentropic.so` with `ctypes` and calls the pure-C `entropic.h` facade. Memory crosses that boundary by explicit ownership rules: engine-returned `char*` must be freed with `entropic_free()`, and buffers the engine will free must come from `entropic_alloc()`.

**How Python reaches the engine**

1. **Locate the library.** `python/src/entropic/_loader.py` `find()` searches, in order: `$ENTROPIC_LIB`, then `$ENTROPIC_HOME` (nested and flat layouts), then `~/.entropic/...`, then `ctypes.util.find_library("rentropic")`. It returns `None` if nothing resolves, and the CLI turns that into an "run `entropic install-engine`" error.
2. **Bind the C ABI.** `python/src/entropic/_bindings.py` is generated by `scripts/gen_bindings.py` from `entropic.h` and marked "generated, do not edit." Every exported function goes through `_bind(name, restype, *argtypes)` (`_bindings.py:35`), which pins `restype` and `argtypes` on the `.so` symbol. Structs become `ctypes.Structure` subclasses and callbacks become `CFUNCTYPE` typedefs.
3. **Hooks run the other way.** `python/src/entropic/hooks.py` `_build_trampoline` (`:140`) wraps a Python callable in a `HOOK_CB` `CFUNCTYPE`. The C engine calls back into Python through it.

**Memory rules across the boundary**

| Direction | Rule | Evidence |
|---|---|---|
| Engine → caller (`char*` returns, e.g. `entropic_run`'s `result_json`) | Caller owns it; free with `entropic_free()`. `NULL` is a no-op. | `entropic.h` file docs; `entropic_run` doc ("caller must free with entropic_free()"); `entropic_free` is `free(ptr)` at `src/facade/entropic.cpp:1954` |
| Caller → engine (buffers the engine will free, e.g. hook `modified_json`) | Must be allocated with `entropic_alloc()` (`malloc` at `entropic.cpp:1944`), or the engine's `free()` is undefined behaviour. | `entropic_alloc` doc; `entropic.h` file docs |
| `const char*` returns | Owned by the handle; valid only until the next call on that handle. Do not free. | `entropic.h` file docs |
| Plugin/backend strings | Same pattern: caller-owned, freed with `entropic_free()`. | `i_mcp_server.h`, `i_inference_backend.h`, `i_inference_callbacks.h` file docs |
| Python → engine via hooks | `_alloc_c_string` (`hooks.py:123`) and the trampoline (`:162`) use `entropic_alloc` and `memmove` the bytes, so the engine's `free()` matches. | `hooks.py` source |
| Python exceptions | Must not escape the trampoline into C. The trampoline catches them, prints the traceback, and returns pass-through (`rc = 0`). | `hooks.py:140-175` |
| Threading | Per the header: `entropic_run` is serialized per handle, `entropic_free`/`entropic_alloc` are thread-safe, and init/destroy must not race other calls on the same handle. | `entropic.h` file docs; `entropic_run` `@threadsafety` |
| Errors | Return an `entropic_error_t`; the message is fetched with `entropic_last_error(handle)`. No C++ exceptions cross the `.so` boundary. | `entropic.h` file docs; `entropic_run`'s try/catch converts exceptions to error codes |

**Gaps I could not settle from the index**

- I found no Python code that calls `entropic_free` on the `result_json` from `entropic_run` or similar. The `entropic_free` callers in the index are C++ facade code, examples, and tests. I did not find the Python engine class that wraps `entropic_run`, so I can't confirm whether the Python layer copies and frees these strings correctly or leaks them. That needs a check of the Python engine wrapper, which the index does not surface.
- The C++ side's internal `free()` calls (for example `fire_pre_hook` in `engine.cpp:1527`) show the engine freeing hook output with plain `free()`. That only matches `entropic_alloc` because `entropic_alloc` is `malloc`. If the allocator ever changes, the pairing breaks.
