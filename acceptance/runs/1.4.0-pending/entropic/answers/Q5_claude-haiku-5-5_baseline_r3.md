**Short answer:** Python does not embed the engine or use a compiled extension. It loads `librentropic.so` with `ctypes` and calls the pure-C API in `entropic.h`. Memory crosses the boundary by explicit rules: the engine allocates what it returns and the caller frees it with `entropic_free()`, and anything passed the other way must come from `entropic_alloc()`.

## How Python reaches the engine

```
Python code
  └─ entropic/_bindings.py      generated by scripts/gen_bindings.py from entropic.h
       └─ _bind(name, restype, *argtypes)   sets ctypes restype/argtypes
            └─ ctypes.CDLL(librentropic.so)   found by _loader.py
                 └─ C facade (entropic.h) → C++ internals inside the .so
```

- **Library lookup** (`python/src/entropic/_loader.py`): `$ENTROPIC_LIB`, then `$ENTROPIC_HOME`, then `~/.entropic/...`, then `ctypes.util.find_library`.
- **Bindings are generated.** `scripts/gen_bindings.py` parses `entropic.h` and the type headers and emits `_bindings.py` and `_bindings_manifest.py`. CLAUDE.md design rule 15 is the source for this. Hand edits will drift.
- **There is no `EntropicEngine` class.** The package is a flat set of C-ABI symbols, per the note in `__init__.py`.
- **Callbacks** are `CFUNCTYPE` trampolines (`HOOK_CB`, `TOKEN_CB`, `STREAM_OBSERVER_CB`, and others). Python keeps them alive in per-handle dicts (`hooks.py` `_bound`, `streams.py` `_observers`, `helpers.py` `_BCB`), because the engine holds only the raw function pointer.

## Memory rules at the boundary

These come from the header's "Memory ownership" block (`entropic.h` lines 32–37) and the function-level `@par Memory ownership` notes.

| Direction | Rule | Python side |
|---|---|---|
| Engine → caller, `char*` out-param (e.g. `entropic_run`) | Caller owns it. Free with `entropic_free()`. | Bindings return raw `c_char_p`. Nothing in `python/src` wraps these in a free, so the caller must free it. |
| Engine → caller, `const char*` return | Owned by the handle. Valid until the next call on that handle. | Copy it out immediately. `c_char_p` conversion does this. |
| Engine → callback arguments (token pointer, delegation request/result) | Valid only for the callback's duration. Copy to keep. | `streams.py` uses `string_at`, which copies. Correct. |
| Caller → engine buffers the engine will free (e.g. hook `modified_json`) | Must be allocated with `entropic_alloc()`. | `hooks.py` `_build_trampoline` does this. The Python string is copied into engine memory, and the trampoline only allocates when the hook returns a value. |
| Static strings (e.g. `entropic_version()`) | Do not free. | Bound as `c_char_p`. |
| Handle | `entropic_create` / `entropic_destroy`. Init/destroy is single-threaded. Calls on one handle are serialized. | Raw `c_void_p`. Nothing in the package wraps it in a context manager, so the caller must destroy it. |

**Rules for errors and callbacks:**
- Exceptions never cross the `.so` boundary. C++ catches them and returns `entropic_error_t` (architecture doc, error-handling section).
- Python callbacks must not let an exception escape into C. Trampolines catch, print, and return a neutral value.
- Callbacks must not call back into the entropic API on the same handle (the `on_token` doc says this explicitly, with a deadlock warning).

## Things I'd flag

1. **Stale doc reference.** Header comments at `entropic.h:701` and `:812` say to free with `entropic_free_string`. That symbol is not declared anywhere. The only free function is `entropic_free()`. A reader following the comments would call a nonexistent symbol.
2. **Result-freeing is left to the caller in Python.** Since the wrapper is flat, every Python call to `entropic_run` and similar functions must pair with `entropic_free` by hand. This is easy to leak and worth a helper.
3. **Keepalive keys are handle addresses.** `streams.py` and `hooks.py` key their keepalive dicts by the handle's pointer value. I did not verify whether `entropic_destroy` on the Python side clears those entries. If it doesn't, a reused address could pick up a stale trampoline. This is unverified, not a confirmed bug.
4. **Input string lifetime is not documented.** I did not find a statement on whether the engine copies `const char*` inputs (e.g. `entropic_run`'s `input`) or keeps the pointer. Python's `bytes` buffers are only valid for the call. Check the implementation before relying on either behavior.
