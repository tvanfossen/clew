Python reaches the engine through a flat, auto-generated `ctypes` binding over `librentropic.so`. There is no C++ object or pybind layer. The ownership rules are in the header, and the Python side follows them only partly.

## How the call path works

```
Python code
  │  import entropic  (lazy PEP 562 exports)
  ▼
entropic/_bindings.py      ← generated by scripts/gen_bindings.py from entropic.h
  │  _bind("entropic_run", restype, argtypes…)
  ▼
entropic/_loader.py        ← ctypes.CDLL(librentropic.so), resolved via $ENTROPIC_LIB, $ENTROPIC_HOME, ~/.entropic/…
  │
  ▼
entropic.h  (pure C ABI, extern "C", ENTROPIC_EXPORT)
  │  opaque entropic_handle_t (void*)
  ▼
src/facade/entropic.cpp    ← C++ behind the boundary; exceptions never cross
```

- **Binding generation.** `_bindings.py` says it is auto-generated and must not be edited. A pre-commit check (`inv gen-bindings --check`) fails if it drifts from the header. `_bindings_manifest.py` drives the lazy exports.
- **Types.** The handle is `c_void_p`. Enums, structs and callback typedefs such as `HOOK_CB`, `TOKEN_CB` and `STREAM_OBSERVER_CB` are `CFUNCTYPE`/`Structure` mirrors of the header.
- **Callbacks.** Python functions are wrapped in `CFUNCTYPE` trampolines. `hooks.py` and `streams.py` keep these alive in module-level dicts keyed by handle address, because a collected trampoline would be a dangling call from C.

## Memory rules at the boundary

The header's "Memory ownership" block (`entropic.h`) sets three rules:

1. **Engine-returned `char*` belongs to the caller.** Free it with `entropic_free()`. `entropic_run` is the example: its `char** result_json` out-param "must be freed with entropic_free()". `entropic_free` is `free()` in `src/facade/entropic.cpp:1954`.
2. **Buffers the engine will free must come from `entropic_alloc()`.** Python must not use `ctypes.create_string_buffer` or any other Python-owned memory for these. `entropic_alloc` is `malloc()` (`entropic.cpp:1944`). `hooks.py::_alloc_c_string` and the hook trampoline use it for hook `modified_json`.
3. **`const char*` returns are owned by the handle** and are valid only until the next call on that handle. Copy them immediately. `ctypes.c_char_p` restype does this, because it converts to `bytes` on return.

Both sides use the same libc allocator, so the `malloc`/`free` pairing holds. The core hook registry calls `free()` on each `modified` buffer it receives (`src/core/hook_registry.cpp:160-255`), which matches `entropic_alloc`.

Other rules that follow from the code:

- **Callback payloads are borrowed.** The `TOKEN_CB` token buffer belongs to the engine and is valid only during the call. `streams.py:71` copies it with `ctypes.string_at(ptr, length)`, which is correct.
- **Python exceptions must not escape.** The hook trampoline and the token observer both catch and print them, because an exception unwinding into C is undefined behaviour.
- **Out-params returned from C are yours to free.** `ctypes` only copies the value. It does not free anything, so the pointer must be released explicitly.

## Gaps I found

These come from reading the code. I did not run anything to confirm them.

1. **No Python wrapper frees `entropic_run` results.** The only `entropic_free` in the Python package is the binding itself. Nothing in `python/src/entropic/` calls `entropic_run`, and the bindings only expose the raw ctypes function. A caller who reads `out.value` and discards `out` leaks the result. The fix is to keep the pointer and call `entropic_free(ctypes.cast(out, ctypes.c_void_p))` (I have not verified that a bare `c_char_p` is accepted directly). The wrapper gap is what I'd fix first.
2. **Possible stale hook binding after handle reuse.** `hooks.register_hooks()` keys `_bound` by the handle's address and never removes entries on `entropic_destroy`. If a new handle lands at the same address, the dedup check may skip binding hooks that the new C-side handle has never seen. I have not reproduced this.
3. **Per-token UTF-8 decode.** `streams.py` decodes each token with `errors="replace"`, so a multi-byte codepoint split across tokens would come out as replacement characters. Whether the engine emits split codepoints depends on the token stream, which I did not check.
