**Short answer:** a call runs only if it clears a fixed chain of checks in `ToolExecutor`. The allow and deny lists feed two of those checks. The deny list is enforced later, inside `ServerManager::execute`, not in the approval step.

```
model emits tool call
  └─ process_tool_calls → sort, truncate to per-turn limit
      └─ process_single_call
          1. PRE_TOOL_CALL hook (can cancel)
          2. check_call_preconditions
             a. anti-spiral hard block
             b. schema
             c. MCP authorization
             d. tier allowed
             e. duplicate-call check
             f. check_approval_pc  ← allow list / auto-approve / callback
          3. execute_tool
             └─ ServerManager::execute
                 ├─ is_denied(tool, pattern)? → "Permission denied" JSON, call stops
                 └─ route_tool_call → the MCP server runs the tool
          4. finalize_tool_call (post hook, history)
```

**Approval step (`check_approval`, `src/mcp/tool_executor.cpp:161`).** Approved if any of these holds:
- `loop_config_.auto_approve_tools` is set. I did not confirm how this maps to `permissions.auto_approve` in config.
- `ServerManager::is_explicitly_allowed` matches an allow pattern.
- An `on_tool_call` callback is registered. See the issue below.

Otherwise the call is denied with "Permission denied", and the code logs "No approval callback — denying".

**What an allow pattern does.** Patterns are matched by `PermissionManager::pattern_matches` (`src/mcp/permission_manager.cpp:101`):
- The text before the first `:` is an fnmatch glob on the fully-qualified tool name, e.g. `filesystem.*`.
- With no `:`, the tool-name match is enough. A bare `bash.execute` allows every call to that tool.
- With a `:`, the part after it is an fnmatch glob on the argument pattern built by `args_to_pattern` (`src/mcp/server_manager.cpp:426`). That is the first argument's string value, or `*` for empty, non-object, or non-string-first-argument JSON.
- Matching is `fnmatch` with flags 0, so `*` also matches `/`, spaces, and shell metacharacters.

An allow hit skips the prompt. It does not bypass the deny check, which runs later.

**What a deny pattern does.** `is_denied` uses the same matcher, but only in `ServerManager::execute` (`src/mcp/server_manager.cpp:153`). A match returns an error result without running the tool, and it is enforced regardless of allow or auto-approve. The header's "deny takes precedence" holds in practice because of this placement, even though `check_approval` never consults the deny list.

**Patterns generated by "Always Allow/Deny".**
- `BashServer::get_permission_pattern` (`src/mcp/servers/bash.cpp:200`) produces `execute:{base_cmd} *`, e.g. `bash.execute:pytest *`. The base command is the text before the first space.
- `PermissionPersister::save_permission` (`src/storage/permission_persister.cpp:227`) writes the pattern into `permissions.allow` or `permissions.deny` in the project YAML.

**Issues found while reading:**
1. **The approval callback never denies.** In `check_approval`, if `on_tool_call` is set, `approved` is forced to `true`. The callback returns `void`, so a frontend cannot refuse through it. The header comment says tools are "approved via callback", which contradicts the code. Unless the frontend blocks inside the callback, which I could not check from the index, the prompt is notify-only.
2. **Bash allow patterns can be overbroad.** `execute:pytest *` is matched by fnmatch, so `*` matches `; rm -rf ~` or `&& curl …`. Nothing I read splits the command on shell operators. An "Always Allow" on one command therefore approves chained commands too.
3. **Non-string first argument.** `args_to_pattern` returns `*` for it, so an argument-scoped allow rule such as `tool:/safe/*` cannot match that call.

I did not verify the frontend side of the callback or the `auto_approve` mapping, so both are open questions.
