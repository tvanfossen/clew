Python reaches the engine through a ctypes binding to the C ABI in `librentropic.so`. There is no C++ crossing the boundary, and the memory rules are about who allocates and who frees.

**How the call path is built**

```
Python caller
  └─ entropic/hooks.py, streams.py, mcp.py      (pythonic facades: dict→JSON, decorators, lifetime registries)
       └─ entropic/_bindings.py                  (ctypes functions, IntEnums, Structures, CFUNCTYPE typedefs)
            └─ entropic/_loader.py  → librentropic.so   (located via $ENTROPIC_LIB, $ENTROPIC_HOME, ~/.entropic, ldconfig)
                 └─ include/entropic/entropic.h  (pure C API, opaque entropic_handle_t)
                      └─ src/facade/entropic.cpp  (C++ behind the C surface)
```

- `_bindings.py` is generated by `scripts/gen_bindings.py` from the C header, and its banner says "do not edit". It covers every `ENTROPIC_EXPORT` symbol, about 220 of them.
- `_loader.py` resolves the library path. If nothing resolves, `find()` returns `None` and the CLI tells the user to run `entropic install-engine`.
- The facades add the Python-side conveniences. `hooks.py` marshals dict↔JSON and keeps callback wrappers alive. `streams.py` wraps the stream observer. `mcp.py` turns kwargs into the JSON that `entropic_register_mcp_server` expects.
- The C++ side never throws across the boundary. The design rules say so explicitly: exceptions do not cross `.so` boundaries, errors come back as codes plus callbacks.

**Memory rules that cross the boundary**

1. **Engine-returned strings belong to the caller.** Any function returning `char*` transfers ownership. Free it with `entropic_free()`. `entropic_run` is the example: it writes a newly allocated JSON result into `result_json`, and the caller must free it. The same rule applies to the backend and MCP interfaces.
2. **Engine-owned `const char*` values are not freed by the caller.** They belong to the handle and stay valid only until the next call on that handle. Copy them if you need them longer.
3. **Buffers the engine will free must come from `entropic_alloc()`.** The engine calls `free()` on them, so they must come from the same allocator. `hooks.py` follows this: `_alloc_c_string` and the hook trampoline write `modified_json` through `entropic_alloc`. `entropic_alloc` is a thin wrapper around `malloc`, and `entropic_free` is a thin wrapper around `free`.
4. **Python must keep callbacks alive.** A `CFUNCTYPE` wrapper that Python garbage-collects while C still holds its pointer leads to a dangling call. `hooks.py` exists largely to prevent this, and `helpers.py` documents the same requirement for the delegation callbacks, which must be held for the engine's lifetime.
5. **Python exceptions do not cross into C.** The hook trampoline catches everything, prints the traceback, and returns 0, which passes the call through unmodified. A hook that raises therefore fails silently from the engine's point of view.
6. **Callbacks can fire on other threads.** The stream observer may be called from the engine thread and from the external-bridge worker thread, so Python callbacks must be thread-safe. Setting the observer before `entropic_configure()` is allowed.
7. **Strings are sanitized at ownership boundaries.** UTF-8 is validated and replaced at each point where bytes change owner, including hook output that crosses a plugin `.so`. Interior code is not sanitized again.
8. **Handles have a threading contract.** Per-handle calls are serialized. `entropic_destroy` must not race with other calls on the same handle, and afterward the handle is invalid.
