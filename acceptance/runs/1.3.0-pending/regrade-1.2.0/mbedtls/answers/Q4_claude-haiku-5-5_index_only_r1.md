A negative return code is turned into text in `library/error.c` by `mbedtls_strerror()`, which splits the code into a high-level and a low-level part and looks each part up in a generated switch. Nothing is looked up by a runtime table, and a contributor who adds a code does not edit `error.c`.

**The path, step by step**

```
caller: ret = -0x0030  (or any negative Mbed TLS code)
  │
  ▼
mbedtls_strerror(ret, buf, buflen)          library/error.c:792
  │  buflen==0 → return; memset(buf,0)
  │  ret = -ret  (take the magnitude)
  │
  ├─ high bits (ret & 0xFF80) ≠ 0?
  │     mbedtls_high_level_strerr(ret)       error.c:174  (switch, module → "CIPHER - ..." etc.)
  │     NULL? → "UNKNOWN ERROR CODE (%04X)"
  │     if the module is SSL fatal alert → return early, skip low level
  │
  ├─ low bits (ret & ~0xFF80) == 0? → return (high-level text only)
  │
  ├─ if high text exists, append " : "
  │
  └─ mbedtls_low_level_strerr(ret)           error.c:537  (switch, "AES - Invalid key length" etc.)
        NULL? → "UNKNOWN ERROR CODE (%04X)"
```

So a composite code such as `-(high | low)` comes out as `"MODULE - high text : low text"`. A code with only low bits gets only the low-level text. The function returns `void`, always null-terminates, and truncates to `buflen`.

The lookup tables inside `mbedtls_high_level_strerr` and `mbedtls_low_level_strerr` are each a `switch` over `-(MBEDTLS_ERR_xxx)` case labels. Each case is wrapped in `#if defined(MBEDTLS_xxx_C)`, so a module that is compiled out contributes no strings. The whole file is gated on `MBEDTLS_ERROR_C` (and the `MBEDTLS_ERROR_STRERROR_DUMMY` symbol, which the index reports as gating eight sites in `error.c`).

**Where the table comes from**

`library/error.c` is not hand-written. The index shows it is generated by `scripts/generate_errors.pl`: `library/CMakeLists.txt:134` runs a custom command that calls `generate_errors.pl` with `include/mbedtls` and `scripts/data_files`, and writes `error.c` into the build directory. The command depends on `error_headers` and `scripts/data_files/error.fmt`. The generator's file-level doc says only "Generate error.c".

**What a contributor does to add one**

1. Add a `#define MBEDTLS_ERR_<MODULE>_<NAME> -0x....` in the module's public header under `include/mbedtls/`, with its doc comment. The value must be negative and must sit in that module's band of the code space, not collide with an existing one. Note that the high-level and low-level bands are split by the `0xFF80` mask, so a new code must fit the band its module owns.
2. Make sure that header is one the generator reads. It takes the `error_headers` list from the CMake setup, so a header in that list is picked up automatically.
3. Rebuild. The custom command regenerates `error.c`, and the new case appears under the module's `#if defined(MBEDTLS_<MODULE>_C)` block.
4. Do not hand-edit `library/error.c`; the next build overwrites it.
5. Add a test and a ChangeLog entry, following the repo's existing pattern. The index does not show the test data file, so I cannot confirm the exact location.

If you skip step 3 or the header is not read, the code falls through to `UNKNOWN ERROR CODE (%04X)`, which is the visible symptom of a missing entry.

**What I could not verify from the index**

The index does not hold `scripts/data_files/error.fmt` or the body of `generate_errors.pl` (it reports zero symbols for that file), and it does not show which description comment format the generator parses. Steps 1–3 are confirmed by the CMake command and the generated code; the exact comment syntax the generator expects, and whether a description string must be written separately, need a read of the generator script. I did not inspect the test files.
