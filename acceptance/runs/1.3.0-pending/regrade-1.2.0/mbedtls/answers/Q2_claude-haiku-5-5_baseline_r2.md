**What it does.** `include/mbedtls/private_access.h` makes `MBEDTLS_PRIVATE(member)` expand to `private_##member` by default, and to plain `member` only when `MBEDTLS_ALLOW_PRIVATE_ACCESS` is defined. Public structs use it throughout, e.g. `include/mbedtls/aes.h:64` declares `int MBEDTLS_PRIVATE(nr);`, and `include/mbedtls/ssl.h` has 209 uses. So an application that writes `ctx->state` gets a compile error, because the member is really named `private_state`. The migration guide (`docs/3.0-migration-guide.md:62-74`) describes this as a last resort: `bar.MBEDTLS_PRIVATE(foo)` works, "at your own risk," and may break in a minor release.

This is a source-level gate, not encapsulation. The struct layout stays in the public header, so `sizeof` and offsets are still visible. What the macro buys is that accidental or unsupported field access fails to compile, and the library can rename or reshape fields without that counting as a source break for callers who never reached in. Its real effect is on the spelling of the API, not on ABI.

**Who gets the opt-out.** Three groups, each turned on in a different place:

1. **Library source (the main case).** `library/common.h:132` defines `MBEDTLS_ALLOW_PRIVATE_ACCESS` unconditionally. Its doc comment says that structs are public but their members are private. `library/common.h` is internal and not installed, and 107 library `.c` files include it. Inside those files, `MBEDTLS_PRIVATE(x)` resolves to the real `x`. The order matters: `private_access.h` has a guard, so the first inclusion decides the expansion. The three library files that use the macro directly (`ecdh.c`, `md.c`, `x509_crt.c`) include `common.h` first. `library/ssl_misc.h` includes it too, and `ssl_ciphersuites_internal.h` uses `info->MBEDTLS_PRIVATE(key_exchange)` on the assumption that the including TU has already gone through `common.h`. A public header included before `common.h` in a library TU would silently give that TU the `private_` names and break the build.

2. **Bundled test/diagnostic programs.** `programs/ssl/ssl_client2.c:8` and `programs/ssl/ssl_server2.c:8` define the macro as their first line, before any include. They use it to inspect internal SSL state, and `ssl_context_info.c` reads `ciphersuite_info->MBEDTLS_PRIVATE(...)` fields without the define, which is a different case. For these two programs the consequence is that they bypass the gate entirely.

3. **External consumers.** The `ssl.h` warning (around line 5163) says direct access via `ssl->MBEDTLS_PRIVATE(state)` or by defining the macro is deprecated and could break in any future release. Downstream code that defines the macro opts out of the contract, and the project has no obligation to keep those names stable.

**Test suites** do not define the macro. They spell `ctx.MBEDTLS_PRIVATE(extensions)` (`tests/suites/test_suite_x509write.function:763`) and `MBEDTLS_PRIVATE(key_loaded_mutex)` (`tests/suites/test_suite_psa_crypto.function:1329`). Both the test and the header expand to the same `private_` name, so the code compiles in the gated configuration with no special casing.

**Practical consequence in this tree:** the opt-out is a compile-time switch in library sources and two test drivers, so renaming or reshaping a field is safe for everything inside the library. It is not a runtime or ABI boundary, so a field change still breaks any binary that reads the struct directly.
