**How Python reaches the engine**

Python does not embed or reimplement the engine. The package is a thin `ctypes` shim over `librentropic.so`, the C ABI declared in `include/entropic/entropic.h`. The header is the only public surface, and all functions are pure C with no C++ types crossing the boundary.

- **Loading:** `python/src/entropic/_loader.py` finds `librentropic.so` (`find()` at line 63 checks candidate paths, then falls back to `ctypes.util.find_library("rentropic")`). `entropic install-engine` fetches the native tarball, so the package works before the library exists.
- **Bindings:** `python/src/entropic/_bindings.py` is generated by `scripts/gen_bindings.py` from the headers, with `inv gen-bindings` to write it and `--check` to fail on drift. It exposes one ctypes function per `ENTROPIC_EXPORT` symbol, IntEnums, `Structure` types, and `CFUNCTYPE` callback typedefs. `__init__.py` imports these lazily (PEP 562). There is no `EntropicEngine` class.
- **Convenience layers:** `hooks.py`, `streams.py` and `helpers.py` are pure-Python facades over the callbacks. They are not part of the C ABI.

Call path, for example `entropic_run`:

```
Python  ->  _bindings.entropic_run (ctypes)
        ->  librentropic.so: entropic_run  (src/facade/entropic.cpp:1974)
        ->  handle->engine->run_turn()  (C++ engine, exceptions caught here)
```

Exceptions never cross the boundary. Errors come back as `entropic_error_t` codes, and the message is read with `entropic_last_error(handle)`.

**Memory rules that cross the boundary**

1. **Engine-allocated `char*` results are owned by the caller.** `entropic_run`, `entropic_context_get` and similar functions write a newly allocated string into an out-parameter, and the caller must release it with `entropic_free()`. `entropic_free(NULL)` is a no-op. Both are `malloc`/`free` wrappers (`entropic.cpp:1944` and `1954`). The Python side must free these strings; I could not confirm from the index whether `_bindings` wraps the `char**` returns to do this automatically.
2. **Strings the engine returns as `const char*` belong to the handle.** They stay valid only until the next call on that handle. Do not free them, and copy them if you need them later.
3. **Buffers the engine will free must come from `entropic_alloc()`.** The hook `modified_json` is the main case. `hooks.py` `_alloc_c_string` (line 123) and `_build_trampoline` (line 140) both use `entropic_alloc`, so the engine's `free()` receives memory of the right provenance. Allocating with Python's allocator here would be undefined behaviour.
4. **Python callables must be kept alive.** A `CFUNCTYPE` wrapper that gets garbage-collected leaves C holding a dangling function pointer. `hooks.py` keeps every trampoline in a per-handle list (`_bound`, populated in `register_hooks` at line 179). The helper docs repeat the rule for delegation and attempt-boundary callbacks, which must be stored on the caller side for the engine's lifetime.
5. **Callbacks must return plain ints.** `ctypes` callbacks should return `int(EntDecision.ACCEPT)` rather than an `IntEnum` member (per the `helpers.py` example).
6. **Threading rules come from the header.** Each function documents one of three classes: thread-safe, serialized per handle, or single-threaded init/destroy that must not race other calls on the same handle. Stream observers can fire from the engine thread and from the external-bridge worker thread, so Python token callbacks must be thread-safe (`entropic_set_stream_observer`, `entropic.cpp:2436`). The header also says `entropic_interrupt` is designed to be called from another thread while a run is in progress.
7. **Interface headers are immutable** (repo `.claude/CLAUDE.md`). The Python bindings are regenerated from them, so an ABI change has to go through the header and the generator, not a hand edit to `_bindings.py`.

**Caveats**

- The index did not expose the `ctypes` argtypes/restype wiring for `char**` out-parameters, so I could not confirm how `_bindings` presents those returns to callers. Check `_bindings.py` directly if that matters.
- `tests/unit/test_bindings_abi.py` describes the IntEnums as "hand-curated", while `_bindings.py` says it is fully generated. Those two descriptions do not agree; I did not resolve which is current.
