**How Python reaches the engine**

Python does not embed or wrap the engine in an object model. It loads `librentropic.so` with `ctypes` and calls the C ABI in `include/entropic/entropic.h` directly.

```
Python caller
  │  from entropic import entropic_create, entropic_run, ...
  ▼
entropic/__init__.py       lazy (PEP 562) attribute lookup, so install-engine works before the .so exists
  ▼
entropic/_bindings.py      generated by scripts/gen_bindings.py; every ENTROPIC_EXPORT symbol,
                           IntEnums, ctypes.Structure types, CFUNCTYPE callback typedefs
  │  _bind(name, restype, *argtypes) pins restype/argtypes on each symbol
  ▼
entropic/_loader.py        finds librentropic.so: $ENTROPIC_LIB, then $ENTROPIC_HOME, then
                           ~/.entropic, then ctypes.util.find_library
  ▼
librentropic.so            C ABI facade: src/facade/entropic.cpp
```

- There is no `EntropicEngine` class. The v2.x wrapper is a flat binding because the C ABI is the public surface.
- `_bindings.py` is auto-generated. Hand-editing it is not the workflow; the generator covers every `ENTROPIC_EXPORT` in `entropic.h`.
- The package is pure Python and holds no native code. The engine binary comes from `entropic install-engine` or from a dev build via `ENTROPIC_LIB`.
- `hooks.py` is the one Pythonic layer. It wraps the hook ABI with decorators, JSON marshalling and lifetime tracking.

**Memory rules that cross the boundary**

1. **Strings returned by the engine are caller-owned.** `char*` results transfer ownership and must be released with `entropic_free()`. For example, `entropic_run(handle, input, char** result_json)` returns a newly allocated JSON string that the caller frees. `entropic_free(NULL)` is a no-op.

2. **Buffers the engine will free must come from `entropic_alloc()`.** This applies to hook `modified_json` and any consumer string the engine takes ownership of. Both functions are thin wrappers over `malloc` and `free`, so the rule is about allocator provenance rather than a different heap. Mixing allocators is undefined behaviour.

3. **Strings returned as `const char*` are handle-owned.** They are valid only until the next call on that handle.

4. **Inputs are borrowed.** A string passed in is valid only for the duration of the call. The engine must copy anything it keeps.

5. **Handles are opaque.** No C++ types cross the `.so` boundary. Exceptions do not cross it either; errors come back as `entropic_error_t` codes, with the message retrieved via `entropic_last_error(handle)`.

6. **MCP plugins follow the same rules.** Strings from `list_tools` and `execute` are caller-owned and freed with `entropic_free`. Strings from `name` are server-owned for the handle's lifetime.

**Python-specific hazards in `hooks.py`**

- **Callback lifetime.** A `CFUNCTYPE` wrapper must stay referenced for as long as the engine can call it. A bare `entropic_register_hook(..., HOOK_CB(f), ...)` drops the wrapper and leaves a dangling function pointer. `register_hooks(handle)` avoids this by storing each trampoline in a per-handle list in `_bound`.
- **Output buffer.** The trampoline writes the JSON result with `entropic_alloc` and `ctypes.memmove`, so the engine's `free()` releases a correctly sourced pointer. `_alloc_c_string` follows the same pattern, and its docstring says no Python reference may outlive that free.
- **No exceptions into C.** The trampoline catches exceptions, prints the traceback and returns 0 (pass-through).

**Things I could not confirm from the index, or that look wrong**

- In `_trampoline`, `rc = 1` is set whenever the hook returns a non-None value, even if `entropic_alloc` returned NULL. In that case the engine is told to transform or cancel but receives no `modified_json`. I'd treat this as a likely bug.
- `_bound` is keyed by the handle's address. I did not find anything that removes a handle's entry on `entropic_destroy`. A recycled address could then inherit stale trampolines, or the list could keep callbacks alive past destroy.
- The index shows the raw ctypes bindings but not whether the Python side frees the `char*` returned by `entropic_run` and similar calls, or whether the restype is `c_char_p` (which copies and loses the pointer). Check `entropic/__init__.py` or the public Python helpers for this.
