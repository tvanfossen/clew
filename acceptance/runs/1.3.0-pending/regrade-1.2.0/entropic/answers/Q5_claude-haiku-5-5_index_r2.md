Python reaches the engine through `ctypes` over a flat C ABI in `librentropic.so`, with no C++ types crossing. The memory rules are documented in `include/entropic/entropic.h`, and I checked them against the implementation. I found two real problems on the Python side.

## How the call path works

```
python/src/entropic/*.py          hand-written: hooks, streams, helpers, CLI
  └─ _bindings.py                 GENERATED by scripts/gen_bindings.py from entropic.h
       └─ _loader.py              CDLL(librentropic.so), search order below
            └─ entropic.h         extern "C" ENTROPIC_EXPORT symbols
                 └─ src/facade/entropic.cpp → C++ engine
```

- **Library lookup** (`_loader.py`): `$ENTROPIC_LIB`, then `$ENTROPIC_HOME` nested and flat, then `~/.entropic/...` nested and flat, then `ctypes.util.find_library("rentropic")`.
- **Bindings**: `_bindings.py` says "do not edit". Each symbol is pinned with `_bind(name, restype, *argtypes)`. The engine handle is `c_void_p`. A pre-commit `inv gen-bindings --check` fails if the file drifts from the header.
- **Callbacks** go the other way. C calls a `CFUNCTYPE` trampoline, which decodes the data and calls the Python function.
- There is no `EntropicEngine` class in v2.x. Users call the flat functions directly, or use the `hook`, `register_hooks` and `register_token_observer` helpers.

## Memory rules

| Direction | Rule | Source |
|---|---|---|
| Engine returns `char*` | Caller owns it. Free with `entropic_free()`. | header "Memory ownership" blocks; `entropic_run` doc |
| Python gives engine a buffer the engine frees (e.g. hook `modified_json`) | Allocate with `entropic_alloc()`. | `hooks.py` `_alloc_c_string`, trampoline |
| `const char*` from a handle | Owned by the handle, valid until the next call on that handle. Copy it. | `entropic.h:37` |
| `entropic_version()` | Static. Do not free. | `entropic.h:173` |
| Pointers passed into callbacks (tokens, context JSON, delegation requests) | Engine-owned, valid only for the callback. Copy them. | `entropic.h:355, 1006, 1027`; `streams.py` uses `string_at` |
| `CFUNCTYPE` trampolines | Python must keep a reference, or C calls freed memory. | `hooks.py` `_HookEntry.trampoline`, `streams.py` `_observers` |
| Exceptions | Never cross into C. Trampolines catch, print, and return 0. | `hooks.py`, `streams.py` |

`entropic_alloc` is `malloc` and `entropic_free` is `free` (`src/facade/entropic.cpp:1944, 1954`). Today both sides use the same libc, but the contract requires the pairing anyway, so an allocator swap would not break it.

## Problems I found

1. **Engine-returned strings lose their pointer through the generated bindings.** `_bindings.py:294` binds `entropic_list_mcp_servers` with `restype=c_char_p`. The header says the caller must free the result. ctypes converts a `c_char_p` return to `bytes` and drops the raw address, so `entropic_free` can never be called on it. Every call leaks. `entropic_run` has the same problem through its `POINTER(c_char_p)` out-param: reading `out[0]` returns `bytes`. The only way to recover the address is to cast the out-param to `POINTER(c_void_p)`. I read the generator's type mapping only far enough to see this for these two. `entropic_context_get`, `entropic_metrics_json` and the other `char*` out-params are probably affected too, but I did not check each one. The fix belongs in `scripts/gen_bindings.py`, which should map owned `char*` returns to `c_void_p` and wrap them in a helper that copies and then frees. I have not run this under ctypes. The conclusion comes from ctypes semantics and the code.

2. **Per-handle Python registries are never cleared.** `hooks._bound` and `streams._observers` are keyed by the handle's address. Nothing in the package calls `entropic_destroy`, so the entries outlive the handle. If a new handle reuses the freed address, `register_hooks` checks `any(b.func is entry.func and b.point == entry.point …)` and skips binding. Hooks would then silently not fire on the new handle. This needs address reuse, which is plausible but unverified. The fix is to wrap destroy so it drops the registry entries for that handle.

Nothing was built or run. Both findings come from reading the code.
