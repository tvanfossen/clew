**How Python reaches the engine**

It is plain `ctypes` over `librentropic.so`, with no C++ crossing. `README.md` calls it "a thin ctypes binding over the C ABI — no OOP wrapper", and `docs/getting-started.md` says "the Python surface is the C ABI verbatim."

```
Python code
  └─ entropic/_bindings.py   (auto-generated by scripts/gen_bindings.py from include/entropic/entropic.h)
       └─ _loader.load()  → ctypes.CDLL(librentropic.so)
            └─ extern "C" symbols (ENTROPIC_EXPORT) in src/facade/entropic.cpp
                 └─ C++ engine (exceptions caught at the boundary, returned as entropic_error_t)
```

- `_bindings.py` is generated and pre-commit checked for drift (`inv gen-bindings --check`). Each line is `name = _bind("name", restype, *argtypes)`, which sets `restype`/`argtypes` on the loaded symbol.
- The handle is `entropic_handle_t = ctypes.c_void_p`, an opaque pointer.
- Hand-written helpers sit on top: `hooks.py` (a `register_hooks` registry), `streams.py` (`register_token_observer`), `helpers.py`, and `_bindings_manifest.py`.

**Memory rules**

The header's stated contract (`include/entropic/entropic.h:32-37`, `:238-249`):

1. Functions returning `char*` transfer ownership. The caller frees with `entropic_free()`.
2. `const char*` returns (e.g. `entropic_version`) are static or handle-owned. Do not free them.
3. Anything the engine will free must come from `entropic_alloc()`. The hook `modified_json` is the main case.
4. Inputs (`config_json`, `messages_json`, tool args) are borrowed for the call only.
5. Callback arguments are valid only during the callback. Copy them if you keep them.
6. Exceptions never cross the `.so` boundary; they become error codes.

The Python side mostly follows these. `hooks.py:123-134` and `:154-162` allocate the modified JSON with `entropic_alloc` and hand it to the engine to free. `hooks.py:37-39` and `streams.py:44` keep `CFUNCTYPE` trampolines alive per handle, because a GC'd trampoline would be a use-after-free from C.

**Problems I found**

I did not build or run anything. These come from reading the code.

- **Leaks from `char*` returns bound as `c_char_p`.** `gen_bindings.py:133` maps `char*` to `ctypes.c_char_p`. ctypes then auto-converts the return to `bytes` and discards the pointer, so `entropic_free()` can never be called on it. The affected functions are declared to transfer ownership in the header but bound as `c_char_p` in `_bindings.py`: `entropic_list_mcp_servers` (294), `entropic_adapter_info` and `entropic_adapter_list` (305-306), `entropic_grammar_get`, `_validate` and `_list` (310-312), `entropic_profile_get` and `_list` (315-316), `entropic_list_mcp_keys` and `entropic_serialize_mcp_keys` (322, 324), and `entropic_get_identity_config` and `entropic_list_identities` (332-333). `entropic_free` is never called anywhere in `python/src/entropic`. The generator needs a distinct "owned string" restype that keeps the raw pointer, plus a wrapper that copies and frees.
- **Out-param strings have no documented free path.** `entropic_run` and similar take `POINTER(c_char_p)` (`_bindings.py:263`). The result has to be freed with `entropic_free(ctypes.cast(res, c_void_p))`. `res.value` is a copy and does not free anything. The getting-started example never shows this.
- **Token callback likely mis-typed (unverified).** `TOKEN_CB` and `STREAM_OBSERVER_CB` (`_bindings.py:240-241`) declare the token as `c_char_p`. In a callback, ctypes will probably hand Python a NUL-truncated `bytes` copy rather than a pointer. `streams.py:71` then calls `ctypes.string_at(token_ptr, length)` on that, which would drop embedded NULs and may read past the copy. The fix would be `c_void_p` plus `string_at`. Confirming this needs a run against the built `.so`.

Suggested next step: fix the generator's mapping for owned `char*` returns and for callback token pointers, then add a unit test (`tests/unit/test_bindings_abi.py` already exists) that checks the returned pointer is non-null and freed.
