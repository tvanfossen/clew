## How Python reaches the engine

Python uses **ctypes** against a C ABI. There is no pybind11, cffi, or C++ crossing. The C++ engine ships as `librentropic.so`, and the Python package is a thin layer over its `entropic.h` header.

```
Python app
  │  from entropic import entropic_create, entropic_run, ...
  ▼
_bindings.py   (generated by scripts/gen_bindings.py from entropic.h; "do not edit")
  │  each ENTROPIC_EXPORT → _bind(name, restype, *argtypes)
  │  enums, Structures, CFUNCTYPE callback typedefs mirror the header
  ▼
_loader.py     find() → ctypes.CDLL(librentropic.so)
  │  search order: $ENTROPIC_LIB → $ENTROPIC_HOME (nested, then flat)
  │                → ~/.entropic (nested, then flat) → ldconfig "rentropic"
  ▼
librentropic.so  (C ABI: entropic_create, entropic_run, ...)
  │  facade/entropic.cpp: extern "C" wrappers, exception barrier
  ▼
C++ engine internals
```

- `_loader.py` resolves the library. It does not load it at import time.
- `_bindings.py` loads it once (`_lib = load()`). Every symbol gets explicit `restype` and `argtypes`, so ctypes will not guess types.
- The engine handle is `entropic_handle_t = c_void_p`, an opaque pointer.
- `entropic/__init__.py` imports the binding names lazily (PEP 562), so `entropic install-engine` can run before the `.so` exists.
- The header is the contract. Pre-commit runs `inv gen-bindings --check`, so a drift between `entropic.h` and `_bindings.py` fails the commit.

## Memory rules across the boundary

These come from the ownership block in `include/entropic/entropic.h:32-37`, the allocator functions in `src/facade/entropic.cpp:1944-1956`, and the architecture doc (`docs/architecture-cpp.md:144`, "all cross-`.so` communication uses C types only").

1. **Returned `char*` transfers ownership.** The caller frees it with `entropic_free()`. Functions that return JSON through an out-param (`char** result_json`, for example `entropic_run`) work the same way.
2. **Returned `const char*` is owned by the handle.** It stays valid until the next call on that handle. `entropic_version()` is static and must not be freed.
3. **`entropic_alloc` and `entropic_free` are a matched pair.** Both are `malloc`/`free` in the engine. Any buffer the engine will free itself, such as a hook's `modified_json`, must come from `entropic_alloc`. `hooks.py:45-55` and `hooks.py:80-83` do this.
4. **Exceptions never cross the boundary.** Every `extern "C"` body runs inside a try/catch barrier that maps exceptions to error codes and logs them (`facade/entropic.cpp:50-87`). Python callbacks follow the same rule: the trampolines catch everything, print it, and return a neutral value (`hooks.py:85-91`, `streams.py`).
5. **Callback objects must be kept alive.** A `CFUNCTYPE` wrapper that Python garbage-collects leaves the engine calling freed memory. The package keeps references in `streams._observers` and the per-handle hook registry, and `helpers.py:37` documents the same requirement for users.
6. **Callback-scoped descriptors are engine-owned.** Pointers in delegation request and result structs are valid only during the callback. `helpers.py` copies them with `ctypes.string_at` before returning, which is the correct pattern.

## Problems I found

These are from reading the code. I did not build or run anything.

- **Caller-freed strings are bound as `c_char_p`, which discards the pointer.** Roughly a dozen functions are documented "Caller must free returned string with entropic_free()" but are bound with `restype = c_char_p`. These include `entropic_list_mcp_servers`, `entropic_grammar_get`, `entropic_grammar_validate`, `entropic_grammar_list`, `entropic_profile_get`, `entropic_profile_list`, `entropic_adapter_info`, `entropic_adapter_list`, `entropic_list_mcp_keys`, `entropic_serialize_mcp_keys`, `entropic_get_identity_config`, `entropic_list_identities`, and `entropic_validation_last_result`. A `c_char_p` restype returns a Python `bytes` copy, and the original pointer is gone. Any raw-binding caller who uses these will leak. Nothing in the package calls `entropic_free` (the only references are the binding and manifest lines), so the package itself has no wrapper that frees them. The out-param cases (`POINTER(c_char_p)`) keep the pointer recoverable, but no code path does that either.
- **The header names a function that does not exist.** `entropic.h:701` and `:812` tell callers to free with `entropic_free_string`, and `facade/entropic.cpp:4022` and `:4099` repeat it. The only deallocator defined is `entropic_free`. A caller who follows these comments fails to link. Either the comments should say `entropic_free`, or a `entropic_free_string` alias should be added. Since the header is an immutable contract, the fix is probably the comment, but that is a call for you.

The generator covers every `ENTROPIC_EXPORT` in the header, so the binding list should match the header. The problems above are in how the bindings are typed, not in which symbols they expose. The `restype` problem is the one I would fix first: it is a real leak for any consumer that uses the bindings directly. The cleanest fix is to change those restypes to `c_void_p` and wrap them in a helper that copies the string and then calls `entropic_free`. Fixing that means changing the generator, not `_bindings.py` by hand.
