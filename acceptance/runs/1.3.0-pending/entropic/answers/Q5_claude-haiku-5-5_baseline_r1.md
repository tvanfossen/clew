**Short answer:** Python talks to the engine through `ctypes`, loading `librentropic.so` and calling its plain C API in `entropic.h`. No C++ types cross the boundary. The memory rules are documented in the header, but the Python side does not fully follow them, and I found a leak in the bindings.

## How Python reaches the engine

```
Python code
  └─ entropic/__init__.py  (lazy __getattr__ re-exports)
       └─ entropic/_bindings.py  (generated by scripts/gen_bindings.py from entropic.h)
            └─ ctypes.CDLL(librentropic.so)   ← entropic/_loader.py find()
                 └─ extern "C" symbols in src/facade/entropic.cpp
                      └─ C++ internals (never exposed)
```

- **Library discovery:** `_loader.find()` checks `$ENTROPIC_LIB`, then `$ENTROPIC_HOME`, then `~/.entropic/...`, and finally `ctypes.util.find_library`.
- **Bindings:** `_bindings.py` is auto-generated and marked do-not-edit. Each C symbol gets `restype`/`argtypes` pinned by a `_bind()` helper. The engine handle is `ctypes.c_void_p`, which is opaque on the Python side.
- **Callbacks:** C function pointers are `CFUNCTYPE` typedefs. Python passes a trampoline and the engine calls back into it.

## Memory rules

These come from `include/entropic/entropic.h` and `docs/architecture-cpp.md`:

| Rule | Source |
|---|---|
| Returned `char*` transfers ownership to the caller. Free with `entropic_free()`. | `entropic.h` memory-ownership block |
| Buffers the engine will free (e.g. hook `modified_json`) must come from `entropic_alloc()`. | `entropic.h`; `hooks.py` uses `entropic_alloc` |
| `const char*` returns are owned by the handle and valid until the next call on that handle. | `entropic.h` |
| Version string has static lifetime. Do not free it. | `entropic_version()` |
| Token pointers in streaming callbacks are valid only for the callback. Copy if you need them. | `entropic_run_streaming` doc |
| Exceptions never cross `.so` boundaries. Errors are return codes, callbacks, or `entropic_last_error`. | `architecture-cpp.md` Error Handling Contract |
| Python keeps a reference to every `CFUNCTYPE` wrapper for as long as the engine may call it. | `streams._observers`, `hooks._bound` |

The Python side does follow the last two rules. `streams.register_token_observer` and `hooks.register_hooks` both store the trampolines per handle. Both trampolines catch Python exceptions so they do not escape into C.

## Where the Python side breaks the rules

1. **Engine-allocated results are never freed from Python.** Functions with `POINTER(c_char_p)` out-params (`entropic_run`, `entropic_run_messages`, `entropic_context_get`, and others) return heap strings. Nothing in `python/src` calls `entropic_free`. The same is true for char-returning functions with `restype = c_char_p`, such as `entropic_list_mcp_servers`, `entropic_grammar_validate`, `entropic_list_mcp_keys`, and `entropic_get_identity_config`. The header says all of these are caller-freed. `c_char_p` restype makes ctypes copy the bytes and discard the pointer, so the buffer can't be freed later. I found this by reading the code and did not run a leak test. A quick check would be to call `entropic_run` in a loop and watch RSS, or run under valgrind.

2. **Stale doc reference.** `entropic.h` (lines 701, 812) and `src/facade/entropic.cpp` (lines 4022, 4099) say to free with `entropic_free_string`. That symbol does not exist. The real function is `entropic_free`.

3. **Hook return path.** If `entropic_alloc` returns NULL, `hooks.py` still returns `rc = 1` and leaves `modified_json` unset. The engine then sees "modified" with no payload. This is a minor issue.

The fix for (1) belongs in the generator: out-params and char-returning functions should use `c_void_p` plus a Python helper that copies the string and calls `entropic_free`. That is a design change to `gen_bindings.py`, so I have not made it. Let me know if you want it written up as a gh issue or patched.
