## How Python reaches the engine

There is no pybind11, Cython, or C extension. The Python package calls `librentropic.so` through `ctypes`.

```
Python caller
  │  entropic.hooks / streams / helpers   (hand-written facade)
  ▼
entropic._bindings                         (generated by scripts/gen_bindings.py from include/entropic/*.h)
  │  _bind(name, restype, *argtypes)  → pins every symbol's ABI
  ▼
ctypes.CDLL(librentropic.so)               (_loader.py picks the path: $ENTROPIC_LIB, $ENTROPIC_HOME, ~/.entropic, ldconfig)
  ▼
extern "C" facade (src/facade/entropic.cpp)  → C++ engine internals
```

- **Loading:** `_loader.load()` returns a `ctypes.CDLL`. `_bindings.py` loads it at import time.
- **Generated surface:** `_bindings.py` is generated from the headers. Enums become `IntEnum`s over `c_int`, the opaque handle is `c_void_p`, structs become `ctypes.Structure`, and callbacks become `CFUNCTYPE`s. `inv gen-bindings --check` runs in pre-commit to catch drift.
- **Facade:** Only the hook, stream-observer, and MCP helpers are hand-written. `entropic/__init__.py` lazily re-exports the generated symbols (PEP 562). There is no `EntropicEngine` class.
- **Threading:** `CDLL` releases the GIL during foreign calls. Callbacks re-acquire it. The header's per-function thread-safety classes still apply on the C side.
- **Exceptions:** C++ exceptions never cross the boundary. The C side catches them and returns error codes. The Python trampolines catch everything and print it, so nothing propagates into C.

## Memory rules at the boundary

These come from the `entropic.h` "Memory ownership" docs and the implementation:

| Case | Rule | Who frees |
|---|---|---|
| `char*` return (e.g. `entropic_run` out-param, `entropic_list_identities`) | Ownership transfers to caller | Caller, via `entropic_free()` |
| `const char*` return (`entropic_version`) | Static; never freed | Nobody |
| `const char*` owned by the handle | Valid until the next call on that handle | Engine |
| Buffer the engine will free (hook `modified_json`) | Must be allocated with `entropic_alloc()` | Engine, via `entropic_free()` |
| Callback arguments (token pointers, delegation request/result, `context_json`) | Valid only for the callback's duration; copy to keep | Engine |
| CFUNCTYPE trampolines | Python must hold a reference for as long as C may call them | Python |

`entropic_alloc` and `entropic_free` are `malloc` and `free` today, but the contract requires using the pair anyway. The Python side follows it: `hooks.py` builds `modified_json` with `entropic_alloc`, and `streams.py` and `helpers.py` copy callback data with `string_at` immediately. Lifetime is handled by keepalive dicts: `hooks._bound`, `streams._observers`, and the caller's variable in the `helpers` example.

## Where the Python side breaks those rules

I found these by reading the code. I did not run anything.

1. **Owned `char*` returns are bound as `c_char_p`, which leaks.** `gen_bindings.py` maps `"char*"` to `ctypes.c_char_p`. That restype makes ctypes copy the string into `bytes` and discard the pointer, so the caller can never call `entropic_free`. The affected bindings are `entropic_list_mcp_servers`, `entropic_adapter_info`, `entropic_adapter_list`, `entropic_grammar_get`, `entropic_grammar_validate`, `entropic_grammar_list`, `entropic_profile_get`, `entropic_profile_list`, `entropic_list_mcp_keys`, `entropic_serialize_mcp_keys`, `entropic_get_identity_config`, `entropic_list_identities`, `entropic_validation_last_result`, and `entropic_get_diagnostic_prompt`. Each call leaks one allocation. Fix: give those functions `restype=c_void_p`, read the bytes with `string_at`, then call `entropic_free`. The root cause is the generator's type map, so fix it there.
2. **`entropic_run` has no wrapper.** Its out-param is `POINTER(c_char_p)`, so the raw address can be recovered, but no Python code in the package calls `entropic_free` anywhere. Callers must cast the pointer to `c_void_p` and free it themselves. The header says this is the caller's job, but the package doesn't help.
3. **Hook trampoline reports success on OOM.** In `hooks._build_trampoline`, `rc = 1` is set even when `entropic_alloc` returns NULL and no `modified_json` is written. The engine then treats the hook as having transformed the payload when it did not. Also, `_alloc_c_string` is unused dead code that duplicates the inline logic.

Items 1 and 2 are the ones that matter. Item 1 is a systematic leak; item 2 is an unwrapped contract.
