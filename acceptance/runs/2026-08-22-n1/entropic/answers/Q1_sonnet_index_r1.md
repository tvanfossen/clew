I found both call sites — `LlamaCppTokenizer::tokenize()` and `LlamaCppTokenizer::detokenize()` in `src/inference/llama_cpp_tokenizer.cpp`. Both call `llama_tokenize`/`llama_token_to_piece` twice, and it's the same underlying pattern in each.

**Why two calls:** these llama.cpp entry points (`vocab->tokenize(...)`, `vocab->token_to_piece(...)`) don't tell you the output size up front, and there's no safe way to guess a buffer big enough in advance — the token count for an arbitrary UTF-8 string, or the surface-string length for a token id, is data-dependent. So the API uses a classic C two-pass sizing idiom, structurally identical to `snprintf(NULL, 0, ...)` followed by `snprintf(buf, size, ...)`:

- **First call** passes a null/too-small buffer (`nullptr, 0` in `tokenize`; a fixed 256-byte stack buffer in `detokenize`). If it doesn't fit, the function returns a *negative* number whose magnitude is the actually-required size — that's the documented contract of `llama_tokenize` ("Returns a negative number on failure - the number of tokens that would have been returned").
- **Second call** is made with a buffer allocated to exactly that required size (`tokens.resize(n)` / `large.resize(-n)`), to actually receive the data.

So the two calls are not doing the same thing with the same arguments — the second call has a different, correctly-sized buffer. They're two phases of one logical operation (measure, then fill), not two attempts at the same operation. `detokenize`'s common case actually only takes one call — the fixed 256-byte buffer covers ordinary token pieces, and the second call only fires when a piece is unusually large.

**If the second call also fails:**
- In `tokenize()`: `actual < 0` is checked. If still negative on the sized second call (a real tokenization failure, not a sizing report this time — the buffer is already correctly sized), it logs `logger->error("Tokenization failed for text of length {}", ...)` and returns an empty `std::vector<int32_t>{}`. No further retry, no throw.
- In `detokenize()`: `n > 0` is checked; if not, it silently returns an empty `std::string{}` — no error log on this path, which is a minor asymmetry with `tokenize()`'s logged failure.

Both callers (`LlamaCppBackend::tokenize_text` / `count_tokens` / detokenize paths) treat these empty results as legitimate degraded outputs, not exceptions — consistent with the project's cross-`.so` rule that exceptions never cross the C boundary.

**Is this retry logic?** No, and I'd push back on that framing. Retry logic re-attempts the *same* operation with the *same* inputs, hoping a transient condition (contention, a flaky external call, a race) resolves on a later attempt. That's not what's happening here — the first call is deliberately not intended to produce the final result at all; it exists purely to ask the API "how big does my buffer need to be," and the second call is a different call, with a different (correctly sized) buffer, that actually performs the encode/decode. There's no non-determinism between the two calls and no expectation the second could differ in outcome for the same inputs if given the same buffer. Calling this "retry" would be describing a `snprintf(NULL,0,...)` → `snprintf(buf,n,...)` pattern as "retrying snprintf," which mischaracterizes it. It's better described as a two-phase measure/fill protocol dictated by the C tokenizer ABI, with a genuine (non-retried) failure path on the second call that degrades to empty output rather than looping.
