**Short answer:** Python never touches a C++ class. It loads `librentropic.so` with `ctypes` and calls the flat C ABI in `include/entropic/entropic.h`. The memory rules are the C header's rules, applied by hand in the Python shims. Those shims have one real defect: several heap-returning functions are bound in a way that leaks.

## How Python reaches the engine

```
user code
  └─ entropic.hooks / streams / mcp / helpers   (hand-written facades)
       └─ entropic._bindings                     (generated: restype/argtypes per symbol)
            └─ ctypes.CDLL(librentropic.so)      (C ABI from entropic.h)
```

- **Loading** (`python/src/entropic/_loader.py`): `find()` checks `$ENTROPIC_LIB`, then `$ENTROPIC_HOME` (nested and flat layouts), then `~/.entropic/...`, then `ctypes.util.find_library("rentropic")`. `load()` returns a `ctypes.CDLL`.
- **Bindings** (`python/src/entropic/_bindings.py`): auto-generated by `scripts/gen_bindings.py` from `entropic.h`. Each symbol goes through `_bind(name, restype, *argtypes)`. The handle is `c_void_p`. Callbacks are `CFUNCTYPE` typedefs, and structs are `ctypes.Structure`. Pre-commit runs `inv gen-bindings --check`, so the file cannot drift from the header.
- **No OOP layer**: `__init__.py` says there is no `EntropicEngine` class. Callers use the flat `entropic_*` functions.

## Memory rules at the boundary

These come from the header's "Memory ownership" and "Thread safety" blocks.

| Direction | Rule | How Python honours it |
|---|---|---|
| Python → C strings | Borrowed for the call. Passed as UTF-8 `bytes`. | `mcp.py` encodes JSON and name to bytes before the call. |
| C → Python `char*` returns | Caller owns them. Must `entropic_free()`. | Only the `_bindings` restype wrappers see these (see defect below). |
| C → Python `const char*` returns | Owned by the handle, valid until the next call on that handle. Copy them. | `entropic_version` (static) is safe as `c_char_p`. |
| Python → C buffers the engine frees | Must come from `entropic_alloc()` so the free matches. | `hooks.py` `_alloc_c_string` / `modified_json` uses `entropic_alloc`. |
| Callback-borrowed pointers | Valid only during the callback. Copy now. | `streams.py` uses `string_at(ptr, len)`; `hooks.py` copies `context_json`. |
| Callback wrappers | Python must keep the `CFUNCTYPE` object alive as long as C can call it. | `streams._observers` and the per-handle hook list in `hooks.py`. |
| Exceptions | Must never cross into C. | Both trampolines catch and `traceback.print_exc()`. |
| Re-entrancy | Token callbacks must not call the API (deadlock). | Documented in the header; the Python side does not enforce it. |
| Structs | Caller-owned struct, engine-owned internal arrays. Free with `entropic_free_logprob_result`. | Not exercised by the Python package. |
| Threading | Per-handle serialization. `create` and `destroy` are single-threaded. | Not enforced in Python. |

Two smaller points:

- Keepalive dicts (`streams._observers`, `hooks._bound`) are never pruned on `entropic_destroy`. That is a small per-handle leak, not a crash.
- `CDLL` releases the GIL during calls, which is what you want. Trampolines re-acquire it.

## The defect: heap `char*` bound as `c_char_p`

The generator's `CTYPE_MAP` (`scripts/gen_bindings.py:132-133`) maps both `const char*` and `char*` to `ctypes.c_char_p`. With `c_char_p` as restype, ctypes copies the result into a Python `bytes` and discards the pointer. The caller can never call `entropic_free` on it. Python package code never calls `entropic_free` at all, so these leak on every call.

Affected bindings (from `_bindings.py`), each documented as "Caller frees with entropic_free()" in the header:

- `entropic_adapter_info` (line 305)
- `entropic_adapter_list` (306)
- `entropic_grammar_get` (310)
- `entropic_grammar_validate` (311), which is also documented to return NULL on success
- `entropic_profile_get` (315)
- `entropic_list_mcp_keys` (322)
- `entropic_get_identity_config` (332)

I did not grep for every `char*` return, so `grammar_list`, `profile_list`, and any others may have the same problem. The C-side ownership is correct; the wrapper loses it. Because the generator is the source, `--check` passes and the drift is invisible.

**Suggested fix (not applied):** make the generator emit an owned-string restype (`c_void_p`) for `char*`, keep `c_char_p` for `const char*`, and add a small helper in `_bindings` or a facade that does `string_at`/decode then `entropic_free`. Add a test that calls one of these and checks the free path. I have not run any tests, and I have not verified that the C side returns the pointers I expect at runtime.
