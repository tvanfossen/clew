**Short answer:** Python never touches C++. It loads `librentropic.so` with `ctypes`, and every call goes through the C API in `include/entropic/entropic.h`. The memory rules are the usual C ones: whoever allocates a buffer that crosses the boundary frees it with the matching function, and nothing C++ crosses the boundary.

**How Python reaches the engine**

```
Python code
  │  entropic.entropic_create(...), entropic_run(...)
  ▼
python/src/entropic/_bindings.py      (auto-generated by scripts/gen_bindings.py)
  │  _bind(name, restype, *argtypes) → getattr(_lib, name), pins restype/argtypes
  ▼
librentropic.so  — C API in include/entropic/entropic.h
  │  opaque entropic_handle_t, pure C types, error codes
  ▼
C++ engine internals (src/, C++ ABI never leaves the .so)
```

- `_bindings.py` is generated from the C header, so the Python signatures track `entropic.h`.
- `hooks.py` adds a callback layer: each Python `@hook` is wrapped in a `CFUNCTYPE` trampoline and registered with `entropic_register_hook`. `register_hooks(handle)` keeps the trampolines in a per-handle list so they outlive the call.
- The repo's rules require that exceptions never cross a `.so` boundary and that errors come back as return codes, callbacks, or `entropic_last_error(handle)`. `_build_trampoline` follows this: it catches every Python exception, prints it, and returns 0 to the engine.

**Memory rules that cross the boundary**

1. **Strings the engine returns are owned by the caller.** `entropic.h` says functions returning `char*` transfer ownership to the caller, and they must be released with `entropic_free()`. `entropic_free(NULL)` is a no-op.
2. **Strings Python hands to the engine must come from `entropic_alloc()`.** Hook results are the example. `_alloc_c_string` and the hook trampoline both copy the UTF-8 bytes into `entropic_alloc` memory and write the pointer to `*modified_json`, and the engine then `free()`s it. The header states that consumer-provided strings the engine will free must use `entropic_alloc`.
3. **The allocator must match.** `entropic_alloc` is `malloc` and `entropic_free` is `free` (`src/facade/entropic.cpp:1944` and `:1954`). Freeing with Python's allocator or any other allocator is undefined.
4. **Exceptions and C++ types never cross.** Every `.so` boundary uses opaque handles, C types, and error codes.
5. **Per-interface string rules.** `i_inference_backend.h`, `i_inference_callbacks.h`, and `i_mcp_server.h` each have a "Memory ownership" section for their own strings (for example, strings returned by generate/complete and by MCP servers). I only saw these as search snippets, not the full text, so I'm not quoting their exact rules.

**Gaps I could not settle from the index**

- Whether the Python wrapper calls `entropic_free` on every `char*` it receives. The binding for `entropic_free` exists (`_bindings.py:262`), but I could not see the call sites in the Python code.
- Whether `_bound` (the per-handle trampoline list) is cleared on `entropic_destroy`. The lookup only shows that entries are appended, so trampolines may outlive the handle. I did not confirm whether this is a leak or intended.
- The `_alloc_c_string` docstring says the caller must make sure "no Python reference outlives that free." That is a lifetime rule, but it does not say how the engine's free is paired with it. I could not verify this from the index.
