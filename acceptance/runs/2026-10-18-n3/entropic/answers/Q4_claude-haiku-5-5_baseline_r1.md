Several parts of entropic run off the caller's thread. Most are guarded by a mutex or join pattern, but one has a lifetime gap.

| Thread | Where | What it does | What keeps it safe |
|---|---|---|---|
| ExternalBridge accept thread | `src/facade/external_bridge.cpp:796`, `accept_loop()` at :917 | Polls the listen socket, checks peer uid, spawns a client thread per connection | `stop()` closes the listen fd, joins the accept thread, shuts down each client fd, then joins client threads. Client list is guarded by `client_threads_mutex_`. `running_` is atomic. |
| ExternalBridge per-client serve threads | :945 | Serves one JSON-RPC connection each | Each thread closes its own fd and sets an atomic `finished` flag. `reap_finished_clients_locked()` joins and erases finished entries. |
| Async ask worker (`run_async_ask`) | :1158, `.detach()` at :1222 | Runs `entropic_run` for `entropic.ask` in the background | Task registry is under `tasks_mutex_`. Sentinel is written under that lock. Broadcasts go through `subscribers_mutex_` with `MSG_DONTWAIT`, and dead fds are dropped. |
| Phase observer callback | `phase_observer_cb`, :1072 | Runs on the engine thread and updates task phase | Takes `tasks_mutex_`. A generation counter (`observer_gen_` / `attached_gen_`) discards stale callbacks after detach. |
| HealthMonitor loop | `src/mcp/health_monitor.cpp:92`, `monitor_loop()` at :137 | Polls MCP servers and reconnects | Watch map is under `watched_mutex_`. Events go into `event_queue_` under `event_mutex_`. Callbacks run on the engine thread via `process_events()` (called from `server_manager.cpp:710`), not on the monitor thread. Stop uses a condvar. |
| Stdio transport | `src/mcp/transport_stdio.cpp:164` | Reads child stderr | `connected_` is atomic. `close()` terminates the child, closes fds, then joins the thread. |
| SSE transport | `src/mcp/transport_sse.cpp:107` | Reads the SSE stream | `connected_` and `running_` are atomic. `close()` stops the HTTP client, notifies `pending_cv_`, then joins. |
| Inference cancel pollers | `src/inference/inference_c_api.cpp:385`, `src/inference/interface_factory.cpp:246`, `src/core/response_generator.cpp:413` | Poll an int or atomic cancel flag every 10 ms and forward it | Each poller is joined before the function returns. The C API poller is RAII in `CancelFlagBridge`. The response-generator observer is joined by hand, and the thread touches only locals that outlive the join. |

**The gap: the detached async worker.** `run_async_ask` captures `this` (the bridge) and `handle_`, then detaches. Nothing counts or joins in-flight workers. `stop()` and `~ExternalBridge()` (:612) do not wait for them. `cancel_inflight_async_tasks` (:434) raises the interrupt, waits at most about 1 second for `phase == "cancelling"` to clear, then bumps the observer generation. That generation bump only silences stale observer callbacks. It does not keep the object alive. If the bridge is destroyed while a worker is still inside `entropic_run`, the worker later locks a destroyed `tasks_mutex_` and calls `broadcast_notification` and `write_sentinel` on freed memory. Destroying the engine handle under a running worker has the same problem. I read this from the code and did not run a test to reproduce it. The fix is a worker counter with a condvar that `stop()` waits on, or a `shared_ptr` owned by the worker. The proposal `.claude/proposals/BACKLOG/P2-20260429-001-async-bridge-io-architecture.md` describes a bounded task pool that would also cover this.

**Smaller items**
- `HealthMonitor::status_callback_` (`health_monitor.h:117`) is a plain `std::function` with no lock. It is safe only if it is set before `start()`. I did not verify the call sites.
- `response_generator.cpp:410`: the observer `std::thread` is joined by hand, not by an RAII guard. An exception between creation and join would reach `std::terminate` from the joinable thread's destructor. C-ABI calls make that unlikely, but it is fragile.

The test suite has concurrency tests in `tests/concurrency/test_thread_safety.cpp` and `tests/unit/mcp/external_bridge_test.cpp`. I did not run them. I did not check whether any of them covers destroying a bridge mid-ask.
