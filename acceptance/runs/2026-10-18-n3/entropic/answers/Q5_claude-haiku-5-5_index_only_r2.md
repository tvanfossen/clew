Python reaches the engine through a flat C ABI. The Python side is a thin `ctypes` shim over `librentropic.so`, and the memory rules are the C header's ownership contracts, plus the lifetime rules the Python facades add for callbacks.

```
Python code
  └─ entropic/hooks.py, streams.py, mcp.py    (ergonomic facades: kwargs, dict→JSON, CFUNCTYPE holding)
       └─ entropic/_bindings.py                (ctypes, generated by scripts/gen_bindings.py from entropic.h)
            └─ librentropic.so                 (C ABI: include/entropic/entropic.h, opaque handle)
                 └─ src/facade/entropic.cpp    (C++ engine behind the C facade)
```

**How the call crosses**

- `_bindings.py` is auto-generated from `entropic.h` by `scripts/gen_bindings.py`. It is a flat ctypes binding with no OOP wrapper. `_bindings_manifest.py` lists its exported names.
- The engine is a `struct entropic_engine` behind an opaque `entropic_handle_t`. Python never sees the struct. Lifecycle is `entropic_create(&handle)` → `entropic_configure(handle, json)` → `entropic_run(...)` → `entropic_destroy(handle)`. `entropic_create` allocates and only initializes the handle. Models load on first generate or on explicit activate.
- Config crosses as a JSON string. The header says JSON is used at the C boundary because any language can produce it. YAML files go through `entropic_configure_from_file()`.
- Errors are return codes (`entropic_error_t`), with `entropic_last_error()` per handle. Exceptions never cross the `.so` boundary (design rule 6 in `.claude/CLAUDE.md`).
- Callbacks are C function pointers plus a `void* user_data`. For example, `entropic_register_hook(handle, point, cb, user_data, priority)` and `entropic_set_stream_observer(handle, observer, user_data)`. Python supplies them as `CFUNCTYPE` trampolines.

**Memory rules that cross the boundary**

1. **Engine-allocated strings are caller-owned.** Functions that return `char*` through an out-parameter, such as `entropic_run(handle, input, &result_json)`, transfer ownership to the caller. Free them with `entropic_free()`, which the header says is for memory "allocated by the engine or `entropic_alloc()`". The Python wrapper is responsible for calling it after copying the value.
2. **Static strings are never freed.** `entropic_version()` returns a static string valid for the process lifetime. The doc says "Do NOT free."
3. **Plugin and backend interfaces follow the same rule.** The MCP-server interface (`i_mcp_server.h`) says returned strings are caller-owned and freed with `entropic_free()`. The inference-callbacks and inference-backend interfaces say result strings are allocated by the callee and freed with the callee's free function.
4. **Handles are not thread-safe for concurrent calls.** Calls are serialized per handle. `entropic_configure` takes a `HandleApiLock`. `entropic_destroy` must not race any other call on the same handle. Different handles are independent.
5. **Callback lifetime is the Python side's problem.** `hooks.py` documents the foot-gun: a `CFUNCTYPE`-wrapped Python callable must be kept referenced for as long as the engine might invoke it, or Python garbage-collects the trampoline. `streams.py` exists to hide this from consumers. `helpers.py` holds the wrapper "for the engine's lifetime" for the same reason.
6. **Stream observers may fire from another thread.** `entropic_set_stream_observer` documents that the observer can run on the engine thread and on the external-bridge worker thread for async MCP tasks. Consumer callbacks must be thread-safe. Python callbacks reacquire the GIL, so a callback that blocks on the GIL from a C thread can stall the engine.
7. **Interface headers are immutable** (`.claude/CLAUDE.md`). The C ABI cannot change without a new proposal, so the generated bindings track `entropic.h` exactly.

**Gaps in what I could verify from the index**

- The index holds the `entropic.h` file-level docs, but the dossier tool does not accept file subjects. I got the ownership rules from search snippets, not the full section, and the snippets were truncated.
- The index does not show how `_bindings.py` handles the GIL or whether ctypes calls release it. Standard ctypes behavior is that `CDLL` calls release the GIL during the foreign call. That is general knowledge, not from this repo.
- `entropic_free` is indexed. The name `entropic_free_string` is not, so the string-free function is `entropic_free`.
