**What it does:** `MBEDTLS_PRIVATE(member)` is a macro in `include/mbedtls/private_access.h` that renames a struct member. By default it expands to `private_##member`, so `ssl->MBEDTLS_PRIVATE(state)` becomes `ssl->private_state`. If `MBEDTLS_ALLOW_PRIVATE_ACCESS` is defined before the header is included, it expands to the plain name. The point is to make accidental access to internals fail at compile time. Application code that reaches for `ssl->state` gets "no member named `state`" instead of silently depending on a layout that can change between releases. It is a source-level guard, not an access-control mechanism. The doc comment on `MBEDTLS_ALLOW_PRIVATE_ACCESS` in `library/common.h:127-131` says the members "are private and should not be accessed by the user."

**Who it's for:**

- **Users of the public API (the default).** Every struct member wrapped in `include/mbedtls/*.h` is mangled unless the user opts out. There are about 209 `MBEDTLS_PRIVATE(` uses in `ssl.h` alone. The `ssl.h` doc comment at lines 5159-5169 spells out the policy: direct access to `ssl->state` is deprecated and may break in any release.

- **The library itself, by default-on opt-out.** `library/common.h:132` defines `MBEDTLS_ALLOW_PRIVATE_ACCESS` unconditionally. Library sources include `"common.h"` before `"mbedtls/ssl.h"`. For example, `library/ssl_msg.c:13,19` and `library/ssl_tls.c:12,18` do this. Inside those translation units, the macro expands to the real member name, so the library writes plain `ssl->state`. This is the main place the opt-out is active: about 107 library `.c` files include `common.h`. The library's own headers and sources only use `MBEDTLS_PRIVATE(` in a few places (`library/ssl_ciphersuites_internal.h`, `pk_internal.h`, `ecdh.c`, `md.c`, `x509_crt.c`), and those expand according to whether `common.h` came first.

- **Two programs that opt out explicitly.** `programs/ssl/ssl_server2.c:8` and `programs/ssl/ssl_client2.c:8` define `MBEDTLS_ALLOW_PRIVATE_ACCESS` at the top of the file, before any includes. These are test and example tools that poke at handshake state directly, so they get the unmangled names. Their code depends on internals and will need updating if those internals change.

- **Everyone else gets the guard.** `programs/ssl/ssl_context_info.c` and `programs/fuzz/fuzz_dtlsserver.c` use `MBEDTLS_PRIVATE(...)` without defining the opt-out. That is the intended pattern for code outside the library: it has to refer to members through the mangled names, and those names are not a stable interface.

**What this means in practice:** an external user who defines `MBEDTLS_ALLOW_PRIVATE_ACCESS` before including Mbed TLS headers is making a deliberate choice to depend on internals. The `ssl.h` warning says the project will not guarantee compatibility for that. Inside the library, the opt-out is on for every translation unit that includes `common.h` first, which is every normal library source. So the guard is a boundary between the library and its users, not a restriction within the library.
