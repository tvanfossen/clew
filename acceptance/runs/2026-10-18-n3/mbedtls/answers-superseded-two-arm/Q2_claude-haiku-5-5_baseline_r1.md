**What it does.** `MBEDTLS_PRIVATE(member)` is a preprocessor macro, defined in `include/mbedtls/private_access.h:14-18`. By default it expands to `private_##member`, so a field like `ssl->state` becomes `ssl->private_state`. Any outside code that touches the field by its normal name fails to compile. When `MBEDTLS_ALLOW_PRIVATE_ACCESS` is defined, the macro expands to the plain name and the field is accessible again.

This is a compile-time guard against accidental use, not a security boundary. It keeps the struct layout and field names out of the public API contract, so Mbed TLS can rename or reorganize internal fields in a minor release without breaking callers who never reached into them. The migration guide says this directly (`docs/3.0-migration-guide.md:68-74`): direct access is "at your own risk," and the escape hatch is `bar.MBEDTLS_PRIVATE(foo)` with the define.

**Who it's for.** The macro is used across about 880 occurrences in 71 files, mostly in public headers (`include/mbedtls/ssl.h` alone has 209). The opt-out is turned on in these places:

1. **Library-internal code.** `library/common.h:127-132` defines `MBEDTLS_ALLOW_PRIVATE_ACCESS` unconditionally. `common.h` is included as the first line of library sources, for example `library/ssl_tls.c:12` before `mbedtls/ssl.h` at line 18. Inside the library, the fields are therefore visible under their real names. The include order matters: the macro is evaluated when the struct header is parsed, so `common.h` has to come before the public headers. Internal headers like `library/ssl_misc.h` and `library/ssl_ciphersuites_internal.h` also use the real names.

2. **Test suites.** Most `tests/suites/*.function` files include `common.h`, for example `test_suite_psa_crypto.function:7`. That pulls in the same opt-out. I have not confirmed from the test build files how the generated test code gets `library/` on its include path, so treat that link as an inference from the include.

3. **Two sample programs.** `programs/ssl/ssl_server2.c:8` and `programs/ssl/ssl_client2.c:8` define the macro themselves, before including `ssl_test_lib.h`. These are test and demo tools that deliberately reach into internals. They are not a model for application code.

**What this means for external code.** A user who does not define the macro gets a compile error if they write `ssl->state` or `ssl->MBEDTLS_PRIVATE(state)`, because the field is named `private_state`. Their only supported route is an accessor function. Where none exists, the escape is to define `MBEDTLS_ALLOW_PRIVATE_ACCESS` before including Mbed TLS headers, or to write `MBEDTLS_PRIVATE(...)` on each access. The `ssl.h` doc at lines 5159-5169 calls the state-field access deprecated and warns it "could be broken in any future release."
