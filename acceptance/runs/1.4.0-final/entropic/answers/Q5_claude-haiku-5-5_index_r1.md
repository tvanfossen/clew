## How Python reaches the engine

Python does not use a C extension, pybind11, or cffi. It loads the shared library with `ctypes` and calls the `extern "C"` ABI directly.

```
Python app
  │  import entropic
  ▼
entropic/_loader.py       find librentropic.so (ENTROPIC_LIB, then ENTROPIC_HOME, then ~/.entropic, then ldconfig); ctypes.CDLL
  ▼
entropic/_bindings.py     GENERATED by scripts/gen_bindings.py from include/entropic/entropic.h + types/*.h
  │                       each C function is pinned via _bind(name, restype, *argtypes)
  ▼  C ABI (no C++ types cross)
src/facade/entropic.cpp   extern "C" entropic_* functions; C++ exceptions caught and turned into entropic_error_t codes
```

- The generator is what keeps the two sides in step. `inv gen-bindings --check` runs in pre-commit and fails if the committed `_bindings.py` drifts from the header.
- Type mapping: the opaque handle is `c_void_p`, enums are `IntEnum`, structs are `ctypes.Structure`, and callbacks are `CFUNCTYPE`.
- Code outside `_bindings.py` (`hooks.py`, `streams.py`, `helpers.py`, `mcp.py`) adds the Pythonic layer: dict/JSON marshalling, decorators, and keeping callbacks alive.

## Memory rules across the boundary

These come from the header comments (`include/entropic/entropic.h` ~L32–35, ~L227–249) and are backed by the implementation (`entropic_alloc` = `malloc`, `entropic_free` = `free`, `src/facade/entropic.cpp:1944` and `:1954`).

| Direction | Rule | Where it matters |
|---|---|---|
| Engine → caller, `char*` return or `char**` out-param | Caller owns it and must call `entropic_free()`. | `entropic_run`, `entropic_context_get`, `entropic_get_identity`, and others. |
| Engine → caller, `const char*` / static | Do not free. | `entropic_version` returns a static string. |
| Caller → engine, buffer the engine will free | Must be allocated with `entropic_alloc()`, not Python's allocator. | Hook `modified_json`. `hooks.py:_alloc_c_string` and the trampoline follow this. |
| Callbacks | Pointers are valid only during the call. Do not re-enter the API from a callback. Exceptions must not escape. Python must hold a reference to the `CFUNCTYPE` object. | `streams.py` keeps `_observers`, `hooks.py` keeps `_HookEntry.trampoline`, `hooks.py` catches all exceptions. |
| Handle | Init and destroy are single-threaded and must not race other calls on the same handle. The handle is invalid after `entropic_destroy`. | `entropic_destroy` at `entropic.cpp:1877`. |

## Where the Python side breaks these rules

1. **Caller-owned strings are lost.** Several `char*` returns are bound with `restype = c_char_p` (`_bindings.py:305`, `:310`–`:312`, `:315`–`:316`, `:322`). Those functions are documented as caller-owned (`entropic.h` ~L1509, ~L1600, ~L1620, ~L1637, ~L1690, ~L1824). With `c_char_p`, ctypes copies the value to `bytes` and drops the pointer, so the buffer can never be freed. The package never calls `entropic_free`. The only mention in `python/src` is its binding declaration. Each of these is a leak on every call. The same applies to out-params declared `POINTER(c_char_p)`, such as `entropic_run`, unless the caller keeps the raw pointer and frees it.
2. **The generator does not model ownership.** `scripts/gen_bindings.py:132–134` maps `char*` straight to `c_char_p` with no ownership information. A generated wrapper cannot follow the free rule without a fix in the generator, such as a `c_void_p` restype plus a helper that copies and frees.
3. **Per-handle registries are keyed by handle address and never cleared.** `hooks.py:84` (`_bound`) and `streams.py:44` (`_observers`) have no removal path that I found. If the allocator reuses a freed handle's address, `register_hooks` will skip the new handle's hooks, because the `any(...)` check at `hooks.py:196` finds the old entries. This is a plausible silent failure; I have not reproduced it.
4. **Doc inconsistency.** The header refers to `entropic_free_string` at `entropic.h:701` and `:812`. No such symbol exists. The real function is `entropic_free`.

## Not verified

- I did not run anything. The findings above come from reading the code.
- `streams.py` declares the token callback argument as `c_char_p` (`_bindings.py:241`) and then calls `string_at(token_ptr, length)`. ctypes converts `c_char_p` callback arguments to `bytes`, which truncates at an embedded NUL. The header's length-carrying API suggests `c_void_p` is the correct type. This needs a runtime check before anyone relies on it.
- I did not confirm whether `const char*` inputs are copied by the engine or only borrowed for the call.
