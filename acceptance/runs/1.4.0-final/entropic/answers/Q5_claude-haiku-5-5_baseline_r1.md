**Short answer:** Python never touches the C++ classes. It loads `librentropic.so` with `ctypes` and calls the flat C ABI in `include/entropic/entropic.h`. Memory crosses the boundary as raw pointers under three rules: whoever gets a `char*` owns it and frees it with `entropic_free()`, strings the engine lends are valid only for the call or until the next call on that handle, and buffers the engine will free must come from `entropic_alloc()`.

**How the call path works**

```
Python (entropic.* / user code)
   │  ctypes.CDLL("librentropic.so")      python/src/entropic/_loader.py
   │  _bind(name, restype, argtypes…)     python/src/entropic/_bindings.py  (auto-generated from entropic.h)
   ▼
C ABI  (extern "C", ENTROPIC_EXPORT)       include/entropic/entropic.h → src/facade/entropic.cpp
   │  opaque entropic_handle_t (void*)
   ▼
C++ engine internals (never cross the .so boundary)
```

- **Loading:** `_loader.find()` checks `$ENTROPIC_LIB`, then `$ENTROPIC_HOME`, then `~/.entropic/entropic/lib/` and `~/.entropic/lib/`, and finally falls back to `ctypes.util.find_library`.
- **Bindings:** `_bindings.py` is generated by `scripts/gen_bindings.py` from the header and marked "do not edit". A pre-commit check fails if it drifts. Each symbol gets pinned `restype`/`argtypes`. Structs are `ctypes.Structure`, and callbacks are `CFUNCTYPE`.
- **Handles:** `entropic_handle_t` is a `c_void_p`. Out-params are passed as `byref(handle)` or `POINTER(c_char_p)`.
- **Callbacks:** Python functions are wrapped as `CFUNCTYPE` trampolines. The trampoline must be kept alive for the handle's lifetime. `hooks.py` and `streams.py` store them in module-level dicts keyed by handle address, and `helpers.py` documents that the caller must hold the reference.
- **Exceptions:** Python exceptions are caught inside the trampoline, printed with `traceback`, and never propagate into C. Per the architecture doc, C++ exceptions don't cross `.so` boundaries either. Errors come back as `entropic_error_t` codes, with detail from `entropic_last_error(handle)`.
- **Public surface:** The package is not an OOP wrapper. There is no `EntropicEngine` class. `__init__.py` lazily re-exports the flat C symbols, plus a few helpers (`mcp.register_server`, `streams.register_token_observer`, `hooks.register_hooks`, `helpers.apply_patch`).

**Memory rules (from `entropic.h` "Memory ownership" and the per-function docs)**

| Case | Rule | Where it applies |
|---|---|---|
| Returned `char*` (`entropic_run` out-param, `entropic_metrics_json`, `entropic_list_mcp_servers`, etc.) | Caller owns it. Free with `entropic_free()`. | Header docs; `src/facade/entropic.cpp` allocates via `alloc_cstr` → `entropic_alloc` → `malloc`. |
| `const char*` returned by `entropic_version()`, `entropic_last_error()`, and similar getters | Static (version) or owned by the handle, valid until the next call on that handle. Never free. | Header docs |
| Buffers the engine will free, such as a hook's `modified_json` | Allocate with `entropic_alloc()`. The engine frees them. | `python/src/entropic/hooks.py` `_trampoline` writes via `entropic_alloc`. `src/core/hook_registry.cpp` calls `free()` on them. |
| Callback arguments (token text, hook context JSON, delegation `patch`, residency/queue strings) | Engine-owned, valid only for the callback's duration. Copy before returning. | Header docs; `streams.py` copies with `ctypes.string_at(token_ptr, length)` before decoding. |
| `entropic_logprob_result_t` | The struct is caller-owned, but its `logprobs`/`tokens` arrays are freed with `entropic_free_logprob_result()`. It nulls the pointers afterward. | `src/facade/entropic.cpp` |
| `entropic_free(NULL)` | No-op. | Header docs |

The cross-cutting rule: never mix allocators. The engine uses `malloc`/`free` behind `entropic_alloc`/`entropic_free`, so Python must not `free` engine memory with its own allocator, and the engine must not free memory Python allocated with `ctypes` buffers. Python-side reads use `ctypes.string_at(ptr, len)` and copy.

**Caveats I found**

- The Python package has no wrapper that frees `entropic_run` results. I grepped `python/` and `tests/*.py` for `entropic_free` and found no call sites. Raw-binding callers must call `entropic_free(out.value)` themselves, or they leak. The C++ tests and the `src/` consumers do free their outputs.
- I confirmed the hook-buffer free in `hook_registry.cpp` but did not trace the full accumulation path (`out_json`) to its final free.
- The rules above come from the header and code comments. I did not run anything to confirm there are no leaks or double frees.
