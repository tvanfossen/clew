**How Python reaches the engine**

Python does not link against C++ or use pybind. It loads the C ABI with `ctypes`:

```
Python API (python/src/entropic/)
   │  hooks.py / streams.py  (Pythonic facades: decorators, dict<->JSON, callbacks)
   ▼
_bindings.py  (generated ctypes declarations)
   │  generated by scripts/gen_bindings.py from include/entropic/entropic.h
   │  run via `inv gen-bindings`; a pre-commit `gen-bindings-check` hook fails on drift
   ▼
_loader.py: load()  ->  ctypes.CDLL("librentropic.so")
   │  find() searches candidate paths, then ctypes.util.find_library
   │  if missing: OSError telling the user to run `entropic install-engine` or set $ENTROPIC_LIB
   ▼
librentropic.so  ->  src/facade/entropic.cpp  (extern "C", ENTROPIC_EXPORT)
```

`entropic.h` is the only contract. Its file docs say all functions are pure C with no C++ types crossing the boundary, and that exceptions never cross it; errors come back as `entropic_error_t` codes, with detail via `entropic_last_error(handle)`. The Python side is therefore a generated shadow of that header plus thin hand-written wrappers.

**Memory rules that cross the boundary**

1. **Engine-allocated return values.** Any `char*` the engine returns transfers ownership to the caller and must be released with `entropic_free()`. `entropic_free` is a plain `free()`, and passing NULL is a no-op.
2. **Consumer-provided buffers the engine frees.** Anything Python hands the engine that the engine will later free (for example, a hook's `modified_json`) must come from `entropic_alloc()`, which is a plain `malloc()`. `python/src/entropic/hooks.py` `_alloc_c_string` does this: it encodes to UTF-8, appends a NUL, `memmove`s into the buffer, and returns the pointer. The docstring notes the caller must ensure no Python reference outlives that free. The contract requires `entropic_alloc` for provenance even though both are currently `malloc`/`free`.
3. **Strings the engine owns.** A `const char*` returned by the engine belongs to the handle and is valid only until the next call on that handle. Python must copy it immediately, not keep the pointer.
4. **Python-owned callbacks must stay referenced.** A `CFUNCTYPE` wrapper garbage-collected while C still holds its pointer leaves C calling freed memory. `hooks.py` keeps a per-handle registry of wrappers alive for this reason. `streams.py` does the same with `_observers[handle_key] = cb`, keyed by the handle's address. Bare `HOOK_CB(f)` passed straight into `entropic_register_hook` is explicitly called out as unsafe.
5. **Exceptions must not cross into C.** The stream observer's trampoline wraps the Python callable in try/except and prints the traceback to stderr. The hook path follows the same principle.
6. **Thread-safety classes.** Each C function documents one of three classes: thread-safe, serialized per handle, or single-threaded init/destroy, which must not race with any other call on that handle.

**Things I could not confirm from the index**

- I did not read the `run()` wrapper or the generated `_bindings.py` body, so I cannot say whether every Python call site frees every returned `char*`. The index shows the C++ examples and tests calling `entropic_free` consistently, but not the Python equivalents.
- I did not find whether `destroy` clears the `_observers` entry for a handle, so the stream observer may outlive its handle's registration. Worth checking in `streams.py` and `entropic_destroy`.
- The index does not list `_loader.py` under that path name in the first lookup; it is at `python/src/entropic/_loader.py`, and that is where I read `find()` and `load()`.
