**Short answer:** the caller passes the negative code to `mbedtls_strerror()`. The function splits the code into a module part and a low-level part, looks each part up in a `switch` table in `library/error.c`, and writes the result into the caller's buffer. The tables are generated by `scripts/generate_errors.pl`, so a new string is added by defining the error macro and regenerating the table, not by hand-editing `error.c`.

**Runtime path**

1. `mbedtls_strerror(int ret, char *buf, size_t buflen)` (`library/error.c:792`, declared in `include/mbedtls/error.h:165`) returns early if `buflen` is 0. It then zeroes the buffer and negates `ret` to get a positive value.
2. The high-level part is `ret & 0xFF80`, which identifies the module. It goes to `mbedtls_high_level_strerr()` (`library/error.c:174`), which switches on the masked value. Each case is guarded by its module's `#if defined(MBEDTLS_<MODULE>_C)`, so only compiled-in modules have strings. The output is a string such as `"CIPHER - Authentication failed (for AEAD modes)"`.
3. If the high-level part is an SSL fatal alert, the function returns early without decoding the low-level part.
4. The low-level part is `ret & ~0xFF80`, which is the specific error within the module. It goes to `mbedtls_low_level_strerr()` (`library/error.c:537`), which switches on it the same way. For example, `-0x0020` is `MBEDTLS_ERR_AES_INVALID_KEY_LENGTH` (`include/mbedtls/aes.h:44`), which maps to `"AES - Invalid key length"`.
5. If both parts are present, the two strings are joined with `" : "`.
6. A code with no table entry becomes `"UNKNOWN ERROR CODE (%04X)"`. Output is always null-terminated and may be truncated to fit `buflen`.

`programs/util/strerror.c` is a command-line wrapper around the same call. It accepts decimal or hex input, including `-0x` values.
