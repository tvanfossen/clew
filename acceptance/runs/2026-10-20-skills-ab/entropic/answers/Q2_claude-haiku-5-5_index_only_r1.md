**How far it reaches into entropic's source:** Mostly the inference layer, and it is contained there.

- **Direct C API users:** `LlamaCppBackend` (`src/inference/llama_cpp_backend.h/.cpp`) is the "15% layer" that calls llama.cpp directly. It loads models, creates contexts, runs the decode loop, and handles mtmd and unload. `LlamaCppSampler` and `LlamaCppSamplerFactory` build llama.cpp's `llama_sampler` chain. `LlamaCppTokenizer` forwards to the vocab API. `AdapterManager` uses the LoRA API. `to_llama_chat` converts messages to `llama_chat_message`.
- **Chat and tool parsing:** `adapters/adapter_registry.cpp` lets llama.cpp's `common_chat` own tool-call parsing for families it has a grammar for. `tool_call_markers.h` derives its markers from the resolved `common_chat` format. `LlamaCppBackend::CommonChatResult` carries the results.
- **Abstraction seams:** `include/entropic/inference/sampler.h` and `tokenizer.h` define abstract seams so the engine can be tested without llama.cpp. Their headers mention llama.cpp only in comments.
- **Public surface:** llama.cpp-specific names show up in `include/entropic/types/config.h` (`llama_log_path`, `ggml_logging`, `frequency_penalty`, `presence_penalty`) and in the backend name `"llama.cpp"` in `backend_capability.h`. `adapter_manager.h` has a `handle` documented as a "llama.cpp adapter handle", which I did not confirm is a raw llama.cpp type. I did not find llama.cpp types in other public declarations, but this index only shows declarations and briefs, so check that before relying on it.
- **Tests:** Many unit and model tests mock llama.cpp symbols at link time (`adapter_manager_test.cpp`, `speculative_compat_test.cpp`, `vocab_only_smoke_test.cpp`).

**Gaps:** The index can't tell you whether the dependency is a build-time link or a dlopen, or how the vendored `stb_image` (mentioned in `image_preprocessor.cpp`) is pulled in. Those need the build files.
