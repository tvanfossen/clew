## How Python reaches the engine

Python never links against the engine. It loads `librentropic.so` at runtime with `ctypes` and calls the C ABI directly. No C++ types cross the boundary.

```
Python (entropic.*)                    librentropic.so (C ABI)
───────────────────                    ───────────────────────
hooks.py / streams.py / mcp.py   ─┐
  (Pythonic facades, keepalives)   │
                                   ▼
_bindings.py  (AUTO-GENERATED)  ── ctypes.CDLL ──►  entropic.h symbols
  restype/argtypes pinned                           (ENTROPIC_EXPORT)
  CFUNCTYPE typedefs (HOOK_CB…)                          │
                                                         ▼
_loader.py  find() → load()                       C facade → C++ engine
  $ENTROPIC_LIB → $ENTROPIC_HOME → ~/.entropic → ldconfig
```

- **`_loader.py`** resolves the `.so` path. It checks `$ENTROPIC_LIB`, then `$ENTROPIC_HOME` (nested and flat layouts), then `~/.entropic`, then `ctypes.util.find_library`. It raises `OSError` if none match.
- **`_bindings.py`** is generated by `scripts/gen_bindings.py` from `entropic.h` and `types/*.h`. Its header says not to edit it, and the pre-commit `gen-bindings --check` fails on drift. Each function is bound with `_bind(name, restype, *argtypes)`. Enums map to `IntEnum`, structs to `ctypes.Structure`, and callbacks to `CFUNCTYPE`.
- **The Pythonic facades** (`hooks.py`, `streams.py`, `mcp.py`, `helpers.py`) sit on top. They add decorators, dict↔JSON marshalling and keepalives.
- `entropic/__init__.py` re-exports the raw bindings lazily through PEP 562 `__getattr__`. The raw C functions are therefore reachable from Python, and the facades are optional.

## Memory rules that cross the boundary

The header (`entropic.h:32-37`) and the per-function `@par Memory ownership` blocks define these rules:

| Direction | Rule | Enforced by |
|---|---|---|
| Engine → caller, `char*` out-param (e.g. `entropic_run`, `entropic_get_identity_config`) | Caller owns it and must call `entropic_free()` | Convention only |
| Engine → caller, `const char*` (e.g. `entropic_version`, `entropic_last_error`) | Static or handle-owned. Do not free. Valid until the next call on that handle | Convention only |
| Caller → engine, buffers the engine will free (hook `modified_json`) | Must come from `entropic_alloc()`, not `malloc`/`new` | `hooks.py` `_alloc_c_string` / trampoline |
| Callback arguments (`ent_delegation_request_t`, token pointers, hook `context_json`) | Engine-owned, valid only for the callback's duration. Copy to keep | Python copies with `string_at` |
| Exceptions | Never cross `.so` | Trampolines wrap calls in `try/except` and `traceback.print_exc()` |
| Callback wrappers (`CFUNCTYPE`) | Python must hold a reference for as long as C may call them | Facade keepalives |

`entropic_alloc` and `entropic_free` are thin wrappers over `malloc` and `free` (`src/facade/entropic.cpp:1944-1956`). That is why memory the engine frees must come from `entropic_alloc`.

## Problems I found while reading

I read these from source and did not run them.

1. **The raw bindings leak owned `char*` returns.** `entropic_run` binds its out-param as `POINTER(c_char_p)` (`_bindings.py:263`), and `entropic_get_identity_config` returns `c_char_p` (`_bindings.py:332`). ctypes copies the string when you read `.value`, so the pointer the engine expects you to free is discarded. Nothing in `python/src/` calls `entropic_free`. Each call leaks unless the caller reads the address with `ctypes.cast(x, c_void_p).value` and frees it. Both functions are documented as "Caller must free with entropic_free()" (`entropic.h:262`, `entropic.h:2017`). This is the main memory hazard on the Python side.

2. **Hook registrations can silently fail after handle reuse.** `hooks.py` keys `_bound` by the handle's address (`hooks.py:195`) and never clears it. Nothing in Python calls `entropic_destroy`. If `malloc` gives a new handle the same address, `register_hooks` sees a stale entry for the same `(func, point)` and skips binding. The new handle then has no hooks, with no error. This is a plausible but unverified scenario. The fix is to clear the entry on destroy or key on something unique per handle.
