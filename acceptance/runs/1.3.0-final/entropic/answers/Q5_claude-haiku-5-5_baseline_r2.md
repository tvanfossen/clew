**Short answer:** Python talks to the engine through `ctypes` over the C ABI of `librentropic.so`. There is no pybind11, cffi, or compiled extension. Memory crosses in three ways: engine-allocated strings the caller must free, engine-owned buffers that are valid only during a callback, and Python-allocated buffers the engine frees. The rules are documented in the header, and the Python side mostly follows them. I found a few gaps.

**How the call path works**

```
Python code
  └─ entropic._bindings  (generated by scripts/gen_bindings.py from entropic.h)
       └─ entropic._loader.load()  → ctypes.CDLL(librentropic.so)
            └─ C facade (src/facade/entropic.cpp, extern "C", ENTROPIC_EXPORT)
                 └─ C++ engine internals (never visible to Python)
```

- **Loader** (`python/src/entropic/_loader.py`): searches `$ENTROPIC_LIB`, then `$ENTROPIC_HOME`, then `~/.entropic/...`, then `ctypes.util.find_library`. It loads the library with `ctypes.CDLL`, which releases the GIL during foreign calls.
- **Bindings** (`python/src/entropic/_bindings.py`): every symbol is bound through `_bind(name, restype, *argtypes)`, which pins the `ctypes` signature. The file is auto-generated, and `inv gen-bindings --check` runs in pre-commit to catch drift from the header.
- **Types**: the handle is `entropic_handle_t = c_void_p`. Structs are `ctypes.Structure` and callbacks are `CFUNCTYPE`.
- **Python-side wrappers**: `hooks.py`, `streams.py`, `helpers.py`, and `mcp.py` add conveniences. They are not a stable API layer.

**Memory rules**

1. **Caller-freed return values.** Functions returning `char*` or taking a `char**` out-param transfer ownership. Free them with `entropic_free()`, which is documented as the pair for `entropic_run`, `entropic_run_as`, `entropic_run_batch`, `entropic_context_get`, and others.
2. **Handle-owned strings.** `const char*` returns, such as `entropic_version()` (static) and `entropic_last_error()` (valid until the next call on that handle), must not be freed.
3. **Callback-scoped pointers.** Token strings, `ent_delegation_request_t`, `ent_delegation_result_t`, and hook `context_json` are engine-owned and valid only during the callback. Copy them before returning. Python does this with `ctypes.string_at(...).decode()` in `hooks.py:154`, `helpers.py:30`, and `streams.py:72`.
4. **Engine-freed buffers.** A hook's `*modified_json` must come from `entropic_alloc()`, not `malloc`. The engine calls `free()` on it. `hooks.py:157–163` does this correctly.
5. **Keep CFUNCTYPE wrappers alive.** A trampoline garbage-collected while C still holds its pointer is a crash. The Python code keeps them in `_bound` (hooks), `_observers` (streams), and a handle-lifetime reference (helpers).
6. **Errors never cross as exceptions.** Functions return `entropic_error_t`. Python `_trampoline` catches all exceptions and returns 0, so nothing propagates into C.
7. **Threading.** Callbacks can fire from the engine or delegation threads. The header requires consumer callbacks to be thread-safe.

**Gaps I found**

- **Raw `entropic_run` out-params are easy to leak.** The binding is `POINTER(c_char_p)`. Reading `out[0]` or `.value` gives a Python copy, and the original pointer is lost. Nothing in `python/src` calls `entropic_run` or `entropic_free` (only the generated binding does), so a caller who uses the raw binding has to `ctypes.cast(out[0], c_void_p)` and free it. Nothing in the package does this for them, and the header doesn't say so.
- **Dangling doc reference.** `entropic.h` lines 701 and 812 and `src/facade/entropic.cpp` lines 4022 and 4099 say to free with `entropic_free_string`. That function does not exist. The real function is `entropic_free`. Doc drift only, but a consumer following it will not link.
- **Architecture rule vs. reality.** The architecture doc forbids `std::string` and other C++ types crossing `.so` boundaries. The Python boundary is clean: only C types cross. I did not audit the C++-to-C++ `.so` boundaries, so I can't confirm that rule holds inside the engine.

I did not build the library or run the Python tests, so the above is from reading the code and docs, not from runtime checks.
