Python reaches the engine through a `ctypes` binding over the C ABI. There is no C++ extension module and no pybind/cffi layer. The memory rules are the C ABI's rules: the owner of each buffer is fixed by which function returns it, and Python code has to follow them by hand.

**How the call path works**

```
Python (entropic package)
  └─ _loader.load()          ctypes.CDLL on librentropic.so
       resolution: $ENTROPIC_LIB → $ENTROPIC_HOME → ~/.entropic → ldconfig
  └─ _bindings.py            generated by scripts/gen_bindings.py
       (from include/entropic/entropic.h; `inv gen-bindings --check` fails on drift)
  └─ hooks.py / helpers.py   hand-written conveniences on top
            │  C ABI (pure C, opaque handles)
            ▼
librentropic.so  src/facade/entropic.cpp  →  C++ engine (AgentEngine, backends)
```

- `entropic.h` is the single public surface. Consumers use opaque `entropic_handle_t` values and never see C++ types.
- The stated design rules are: pure C at every `.so` boundary, exceptions never cross a `.so` boundary (they are caught at the edge and turned into return codes or callbacks), and the Python wrapper is generated from the header.
- Python callbacks are `CFUNCTYPE` wrappers. `hooks.py` keeps a per-handle registry so the wrappers stay alive, because a bare wrapper that gets garbage-collected leaves C calling freed memory.

**Memory rules across the boundary**

1. **Engine-returned `char*` belong to the caller.** Functions such as `entropic_run(handle, input, char** result_json)` allocate the result. The caller must release it with `entropic_free()`. Passing NULL to `entropic_free` is a no-op.
2. **Strings the engine hands out as `const char*` belong to the handle.** `entropic_last_error()` is the example. The pointer stays valid until the next call on that handle, and the caller must not free it.
3. **Buffers the engine will free must come from the engine's allocator.** Any consumer-provided buffer that the engine later frees, such as a hook's `modified_json`, must be allocated with `entropic_alloc()`. In `hooks.py`, `_alloc_c_string` and the trampoline use `entropic_alloc` for this reason. Mixing allocators is undefined behaviour.
4. **Inputs are borrowed.** Strings passed in are only borrowed for the duration of the call, so the caller can free them afterwards.
5. **Plugin and backend interfaces follow the same rule with their own free function.** `i_mcp_server.h` says strings returned by `list_tools` and `execute` are caller-owned and freed with `entropic_free()`. `i_inference_callbacks.h` says results are allocated by the callee and freed with the callee's free function. `i_inference_backend.h` gives the same rule for generate/complete output.
6. **Python may not let an exception reach C.** The hook trampoline wraps the user function in a `try` block, prints the traceback and returns "pass through" on any exception.

**Gaps and caveats**

- The index shows no Python call site of `entropic_free`. I could not confirm whether the generated `entropic_run` wrapper or its helpers release the `result_json` buffer, so a Python caller could leak it. Check that before relying on it.
- In `_build_trampoline`, if `entropic_alloc` returns NULL the trampoline still returns 1 ("transform") without setting `modified_json`. That is a likely bug, not a documented rule. The `_alloc_c_string` path handles the NULL case correctly.
- The index's `entropic.h` file documentation calls `entropic_free` and `entropic_alloc` "the" allocator pair, but it does not state whether the engine's `free` and the CRT `malloc` are the same heap across `.so` boundaries. The implementation is a plain `malloc`/`free` pair, which is safe only when both sides link the same C runtime.
