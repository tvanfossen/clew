## How Python reaches the engine

Python never links against the C++ code. It loads the shared library at runtime through `ctypes`, and the C ABI is the only boundary.

```
Python app
  │  import entropic
  ▼
entropic/__init__.py        PEP 562 lazy re-exports (don't load the .so on import)
  │
entropic/_bindings.py       AUTO-GENERATED by scripts/gen_bindings.py (`inv gen-bindings`)
  │                         pins restype/argtypes per symbol; CFUNCTYPE callbacks; ctypes.Structure
  │  ctypes.CDLL(path)
  ▼
librentropic.so             C ABI: include/entropic/entropic.h → src/facade/entropic.cpp
                            (ENTROPIC_EXPORT symbols only; errors are entropic_error_t codes)
```

- **Loading** (`_loader.py`): `find()` checks `$ENTROPIC_LIB`, then `$ENTROPIC_HOME`, then `~/.entropic/...`, then `ctypes.util.find_library("rentropic")`. `load()` wraps it in `ctypes.CDLL`.
- **Generation**: `_bindings.py` is generated from `entropic.h` and `types/*.h`. The pre-commit `gen-bindings-check` hook fails on drift, so the header is the source of truth.
- **Hand-written facades**: `hooks.py` (`@hook`, `register_hooks`) and `streams.py` (`register_token_observer`) wrap the callback ABI. `mcp.py` and `helpers.py` are the other conveniences.
- **No wrapper class**: the package deliberately exposes flat C symbols (`entropic_create`, `entropic_run_streaming`, …) and no `EntropicEngine` class.

## Memory rules across the boundary

**Documented in `entropic.h`:**

| Kind | Rule | Who frees |
|---|---|---|
| `char*` return / `char**` out-param | Ownership transfers to the caller | Caller, with `entropic_free()` |
| `const char*` return | Owned by the handle, valid until the next call on that handle | Nobody. Don't free it. |
| `entropic_version()` | Static lifetime | Nobody |
| Buffers the engine will free (hook `modified_json`) | Must come from `entropic_alloc()` | Engine, with `free()` |

`entropic_alloc` is `malloc` and `entropic_free` is `free` (`src/facade/entropic.cpp:1944`, `:1954`), so the pairing is only a contract. The rule exists so both sides use the engine's allocator, not Python's.

**Enforced in the Python code:**

- **CFUNCTYPE trampolines must be kept alive.** Python's GC would otherwise free them while C still holds the pointer. `hooks.py` stores each trampoline on its `_HookEntry` inside `_bound[handle]`. `streams.py` stores the observer in `_observers[handle]`.
- **Exceptions never cross into C.** Both trampolines catch `Exception`, print the traceback, and return a pass-through value.
- **Hook output is allocated by the engine's allocator.** `_build_trampoline` calls `entropic_alloc`, copies the JSON with `memmove`, and assigns it to `*modified_json`. The engine frees it (`src/core/hook_registry.cpp:160–169`, `:255`).
- **Token pointers are copied immediately.** `streams.py:71` uses `string_at` inside the callback instead of keeping the pointer.
- **Handles are opaque.** They are `c_void_p`, and the facades key their per-handle state on the handle's address.

## Gaps I found

1. **The raw `entropic_run*` family can leak.** Their `char**` out-param is typed as `POINTER(c_char_p)`, so reading `.value` gives a bytes copy and drops the original pointer. Nothing in the package frees it. Callers must do `entropic_free(ctypes.cast(out, ctypes.c_void_p))` after reading. There's no helper, and the docs don't mention this. I haven't confirmed it against a shipped example.
2. **Hook registry keyed by address, never cleared.** `_bound` (`hooks.py:84`) is only written in `register_hooks`. Python has no destroy wrapper that clears it. If a handle is destroyed and `malloc` gives the next handle the same address, `register_hooks` skips entries it thinks are already bound. The new handle would silently get no hooks. This is plausible from the code; I did not reproduce it.
3. **Dead code.** `_alloc_c_string` (`hooks.py:123`) is never called. The trampoline repeats its logic inline (`hooks.py:159–162`).
4. **Minor:** if `entropic_alloc` returns NULL inside the hook trampoline, the callback still returns `rc = 1` with `*modified_json` unset.

I read the code and did not run anything, so items 1 and 2 are findings from reading, not from tests.
