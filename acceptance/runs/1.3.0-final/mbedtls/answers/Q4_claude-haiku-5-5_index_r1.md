A negative return like `-0x6100` never reaches a lookup table at runtime. `mbedtls_strerror()` splits the value into two fields and looks each one up in a generated `switch`. The tables come from the `#define`s in the public headers.

## Walkthrough

```
ret = -0x6100
   │
   ▼
mbedtls_strerror(ret, buf, buflen)            library/error.c:792
   │  zero buf, negate ret → 0x6100
   ├─ ret & 0xFF80 ≠ 0 ?  ──yes──► mbedtls_high_level_strerr(ret)   error.c:174
   │                                 "CIPHER - Bad input parameters"
   │                                 (NULL → "UNKNOWN ERROR CODE (%04X)")
   │  (SSL fatal alert? → return now, skip low level)
   ├─ low = ret & ~0xFF80 ; low == 0 ? → done
   │
   ├─ append " : "   (only if high part already written)
   ▼
mbedtls_low_level_strerr(ret)                  error.c:537
   (NULL → "UNKNOWN ERROR CODE (%04X)")
```

1. **Sign and split.** The header documents the layout (`include/mbedtls/error.h:14-50`): one sign bit, then the high-level module ID, then module-specific bits, then the low-level bits. The high-level part is `code & 0xFF80`. The low-level part is `code & ~0xFF80`. Both helpers negate their input first, so a caller can pass either sign.
2. **High level.** `mbedtls_high_level_strerr()` is a `switch` over the high part. Each `case` is guarded by its module's `MBEDTLS_<X>_C` macro.
3. **Low level.** `mbedtls_low_level_strerr()` does the same over the low part, for the low-level modules.
4. **Join.** The two strings are joined with `" : "`. Either part can be absent. The test data shows both shapes: `-0x0020` gives `"AES - Invalid key length"` (low only), and `-0x4080` gives `"RSA - Bad input parameters to function"` (high only), per `tests/suites/test_suite_error.data`.
5. **Unknown codes.** An unmatched code falls back to `UNKNOWN ERROR CODE (%04X)`. The output is always NUL-terminated and truncated to `buflen`.

**Where the tables come from.** `library/error.c` is generated by `scripts/generate_errors.pl`. It scans `include/mbedtls/*.h` for `#define MBEDTLS_ERR_… -0x…` lines that carry a Doxygen description, and emits one `case` per code. Nobody edits `error.c` by hand. It is tracked in git and regenerated by the Makefile and CMake rules (`library/Makefile:355-360`, `library/CMakeLists.txt:136-144`). `check-generated-files.sh` regenerates it and diffs the result.

**Gating.** The tables are compiled only under `MBEDTLS_ERROR_C` (`error.c:14`). The outer guard also accepts `MBEDTLS_ERROR_STRERROR_DUMMY` (`error.c:12`). I did not read that dummy branch, so I can't say what it compiles.

## Adding a new code

1. **Define it** in the public header for its module, `include/mbedtls/<module>.h`. Write `#define MBEDTLS_ERR_<MODULE>_<NAME>  -0x…` with a Doxygen description, either a `/**` block before the line or `/**<` after it. Not both.
   - The generator's regex requires the `-0x` form, so decimal values are silently skipped.
   - It rejects a description on both sides, and rejects a before-comment that contains `\name`.
   - It also rejects a duplicate value, so pick an unused code in the module's band (`error.h:14-50`).
2. **Register the module** if it is new. The generator refuses any module name not listed in `@low_level_modules` or `@high_level_modules` (`generate_errors.pl:36-43`) and exits with "Do not know how to handle". The module name is the token after `MBEDTLS_ERR_`. Three names are remapped (`MPI`→`BIGNUM`, `CTR`→`CTR_DRBG`, `HMAC`→`HMAC_DRBG`), and some modules map to several config macros (`generate_errors.pl:122-127`).
3. **Regenerate** `library/error.c`. Building through make or CMake does it, since the headers are dependencies. Then commit the regenerated file, because it is tracked. Run the gate through pre-commit as the repo's AGENTS.md requires.
4. **Add a test row** to `tests/suites/test_suite_error.data`, in the form `depends_on:MBEDTLS_<X>_C` followed by `error_strerror:-0x…:"MODULE - description"`. The test calls `mbedtls_strerror` and compares the string exactly.
5. **Check by hand** if you want a quick look. `programs/util/strerror.c` takes a code and prints its text.

Note that the generator checks uniqueness but not band placement. Keeping a new code inside its module's band is a review concern, not something the build enforces.
