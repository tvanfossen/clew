## Off-caller-thread execution in entropic

Nothing in entropic uses thread pools or `std::async` — every background execution path is a plain `std::thread` (some `.detach()`'d, most joined on teardown). There are nine distinct spawn sites, clustered into three groups: the MCP bridge's I/O loops, transport reader threads, and small cancellation-poller threads that bridge a C-ABI `int*` into an atomic. There's no dedicated "Threading"/"Concurrency" section in `docs/architecture-cpp.md` — the closest architecture-level rule is Design Rule #10 ("atomic state, mutex transitions"), which is scoped to the inference backend's state machine, not to these threads. Where a real cross-thread contract exists, it's documented on the owning class/header instead, and the quality of that documentation varies a lot between classes.

**1. `ExternalBridge` accept loop** (`src/facade/external_bridge.cpp:796`) — polls the unix socket and accepts clients. Safety: `running_` is `std::atomic<bool>`; `listen_fd_` is closed only after `running_` flips and before `join()`, so safety here is ordering, not a lock. Documented in the class header's thread-safety note.

**2. `ExternalBridge` per-client serve threads** (`external_bridge.cpp:945`) — one thread per connection running the request dispatch loop. Safety: the thread handle + fd live in a `client_threads_` vector guarded by `client_threads_mutex_`, each entry carries its own `atomic<bool> finished`; `stop()` locks to move the vector out, then `shutdown()`s each fd outside the lock to unblock blocking `read()`s before joining. `subscribers_` is separately guarded by `subscribers_mutex_`. Well-documented in the header.

**3. `ExternalBridge::run_async_ask`** (`external_bridge.cpp:1158`, detached at `:1222`) — runs an async `entropic.ask` in the background. Safety: all task-table access goes through `tasks_mutex_`; `observer_gen_` is an `atomic<uint64_t>` generation counter incremented under that mutex and checked (without the lock) by the phase-observer callback to discard stale post-detach callbacks. This generation-counter pattern is explicitly called out in comments — it's the one place where "atomic read without a lock" is a deliberate, documented design choice rather than an oversight.

**4. `ResponseGenerator::dispatch_batch_generate`** (`response_generator.cpp:413`) — polls the engine's interrupt flag and mirrors it into a C-ABI cancel int. **This is the one genuine gap**: `cancel_int` is a plain, non-atomic `int` (`response_generator.cpp:404`) written by the observer thread and read across the C-ABI boundary by the calling thread — a real data race, unlike sites #5 and #6 which solve the identical problem with `std::atomic<bool>`. The comment explains the int-boundary rationale but doesn't flag the missing synchronization, and nothing in the architecture doc covers it.

**5–6. `iface_generate_with_cancel`** (`interface_factory.cpp:246`) and **`CancelFlagBridge`** (`inference_c_api.cpp:385`) — same 10ms-poll cancellation-bridge pattern, done correctly: `cancel_flag`/`done` (or `cancel_`/`done_`) are `std::atomic<bool>`, threads are joined (the latter via RAII destructor). Both documented in local comments.

**7. `HealthMonitor::monitor_loop`** (`health_monitor.cpp:92`) — polls watched external MCP servers and posts health events. Safety: `watched_` under `watched_mutex_`, `event_queue_` under `event_mutex_` and drained via lock+swap, `running_` atomic, plus a `wake_cv_`/`wake_mutex_` for early wakeup on stop. This is the best-documented threading contract in the codebase — the header states outright: "status changes are posted to a thread-safe event queue... the engine's main thread drains via `process_events()`. No cross-thread mutation of engine state." The callback into engine code is explicitly restricted to run only on the caller's thread during drain, never from the monitor thread itself.

**8. `StdioTransport::stderr_reader_loop`** (`transport_stdio.cpp:164`) — forwards a child process's stderr to the logger. Safety: `atomic<bool>` for `connected_`/`cancel_flag_`; stdin/stdout I/O is guarded by `io_mutex_`, but the stderr fd is separate and untouched by that mutex — safe by construction (no shared buffer) but less explicitly documented than #7.

**9. `SSETransport::sse_reader_loop`** (`transport_sse.cpp:107`) — reads an SSE stream and matches responses to pending requests by id. Safety: `pending_responses_` guarded by `pending_mutex_` with a `pending_cv_` that `send_request()` blocks on and `close()` notifies to unblock waiters before shutdown; `connected_`/`running_` atomic; `next_request_id_` is `atomic<int>`. Documented in the header.

### Bottom line

The prevailing safety pattern is consistent and mostly sound: atomics for simple flags/counters, mutexes for anything structured (maps, vectors, queues), condition variables where a caller thread needs to block on background-thread progress, and careful join/shutdown ordering to avoid use-after-close on fds. `HealthMonitor` is the model example, with an explicit "no cross-thread engine mutation" rule stated in its header. The one place that pattern isn't followed is `response_generator.cpp:404`'s `cancel_int` — a plain `int` shared across threads where the two sibling implementations (`interface_factory.cpp`, `inference_c_api.cpp`) both correctly use `std::atomic<bool>` for the exact same problem. That's worth fixing to match the established convention, and worth adding to the architecture doc's threading guidance so it doesn't reappear at the next call-cancellation site.
