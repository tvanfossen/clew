Now I have a full picture from the index. Here's what runs off-caller-thread in entropic, and what makes each one safe:

**`ExternalBridge::accept_loop` + per-client threads** (`src/facade/external_bridge.cpp`, spawned from `ExternalBridge::start`)
This is the richest case. `accept_loop` itself runs on its own thread, polling the listen socket every 500ms. For every accepted connection it spawns *another* `std::thread` running `serve_client(fd)` — so this is actually a thread-per-client design, not a single background thread. Safety mechanisms, per the index:
- `SO_PEERCRED` gating (`peer_uid_matches`) rejects cross-uid connections before a serve thread is even spawned (gh#34, v2.1.7).
- `client_threads_mutex_` (RAII `lock_guard`) protects `client_threads_` when a new `ClientThread` is pushed and when `reap_finished_clients_locked()` joins/erases finished ones — the accept thread is both producer and reaper, but the mutex also protects against whatever else touches that vector.
- Each client thread signals completion via `raw->finished.store(true)` (atomic flag) rather than the accept thread reading the `std::thread` state directly — that's the join/reap handshake.
- `stop()` calls `shutdown(fd, SHUT_RDWR)` to unblock a client thread that's parked in a blocking read, closing the race between shutdown and an in-flight `serve_client`.
- Shared state the client threads touch — `tasks_mutex_` (guards the task map: `handle_ask_status`, `run_async_ask`, `update_task_phase`, `cleanup_expired_tasks`, phase observers) and `subscribers_mutex_` (guards the subscriber set: `subscribe`/`unsubscribe`/`broadcast_notification`) — are each taken via RAII guards, so any client thread reading/writing bridge-wide state serializes through those two locks.
- A `HandleLogScope` is captured into the per-client thread so its logs route to the right session log — a correctness detail, not a race-safety one, but notable since it's thread-local plumbing.

**`HealthMonitor::monitor_loop`** (`src/mcp/health_monitor.cpp`, spawned from `HealthMonitor::start`)
Loops with a 500ms wait. `watched_mutex_` (RAII) guards iteration over `watched_` while calling `check_server`; a separate `wake_mutex_` backs a `wake_cv_.wait_for` used purely to make shutdown responsive rather than to protect data. Two distinct mutexes for two distinct concerns (data vs. wake signaling) — not nested per the lock-nesting data.

**`StdioTransport::stderr_reader_loop`** (`src/mcp/transport_stdio.cpp`, spawned from `StdioTransport::open`)
Reads the child process's stderr fd and forwards lines to the logger. The index shows no lock taken inside this function itself — it only reads a fd and calls `logger->warn`. The transport does have an `io_mutex_`, but it's held on the *main*-thread side, in `send_request` (guarding writes to the child's stdin/reads of stdout), not in this reader loop — so stderr forwarding and stdin/stdout I/O are on separate fds and don't contend for the same lock. `connected_` (read here, presumably atomic/bool) is the loop's exit condition, shared with whichever thread manages the transport lifecycle — the index doesn't show it as lock-protected, so I can't confirm from the graph alone whether it's declared atomic; that's a gap you'd need to check the header for.

**`SSETransport::sse_reader_loop`** (`src/mcp/transport_sse.cpp`, spawned from `SSETransport::open`)
Runs `httplib`'s blocking `Get` with a streaming content receiver, parsing SSE lines via `process_sse_line` and setting `connected_ = false` on disconnect. No lock is taken directly inside `sse_reader_loop`, but `SSETransport` does hold a `pending_mutex_` elsewhere (2 acquisitions) — the index doesn't place it inside this function's own section list, so whatever `pending_mutex_` protects (likely a pending-request/response map fed by `process_sse_line`) is guarded on the consumer side, not shown here. Worth confirming in source whether `process_sse_line` itself takes `pending_mutex_`, since dossier on `sse_reader_loop` shows no `sections` for it directly.

**Overall pattern:** every background loop is a `while(running_/connected_)`-style loop over a flag, each with its own narrowly-scoped RAII mutex(es) for the state it actually shares with other threads, plus condition variables or short polling intervals (500ms is a recurring constant) to keep shutdown responsive rather than blocking indefinitely. The one genuinely dynamic, thread-per-connection design is `ExternalBridge`; the other three are fixed, single long-lived background threads.

One honest gap: the index's lock-section data only shows what's captured as an explicit critical section syntactically inside a function body. It doesn't verify that every genuinely shared variable (e.g., `running_`, `connected_` atomics) is declared atomic — that requires reading the class declarations in the headers, which the index didn't surface as part of these dossiers.
