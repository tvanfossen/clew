## How Python reaches the engine

There's no C extension module (`.pyd`/`.so` Python binding, no pybind11/nanobind, no Cython). The bridge is pure **ctypes against the plain-C ABI in `include/entropic/entropic.h`**:

1. **`entropic._loader.load()`** (`python/src/entropic/_loader.py`) resolves `librentropic.so` on disk — `$ENTROPIC_LIB` → `$ENTROPIC_HOME` (nested/flat) → `~/.entropic` (nested/flat) → `ctypes.util.find_library("rentropic")` — and calls `ctypes.CDLL(path)`. If nothing resolves, it raises `OSError` telling the user to run `entropic install-engine`.
2. **`entropic._bindings`** (auto-generated by `scripts/gen_bindings.py`, regenerated via `inv gen-bindings` and checked for drift in pre-commit) loads that `CDLL` once at import time and pins `restype`/`argtypes` on every `ENTROPIC_EXPORT` symbol via a `_bind()` helper. It also mirrors the header's enums as `IntEnum`, its structs (`EntDelegationRequest`, `EntropicLogprobResult`, …) as `ctypes.Structure`, and its callback typedefs as `ctypes.CFUNCTYPE`s (`HOOK_CB`, `TOKEN_CB`, `STATE_OBSERVER_CB`, etc.). The generator claims to cover *every* exported symbol in `entropic.h`, so this is the entire crossing surface — nothing is hand-written or partial.
3. The engine handle itself, `entropic_handle_t`, is just `ctypes.c_void_p` — Python never sees the C++ object behind it, only an opaque pointer it passes back into every subsequent call (`entropic_create` → `entropic_configure*` → `entropic_run*` → `entropic_destroy`), matching the header's "pure C at the boundary, no C++ types cross" rule.
4. Higher-level Python (`entropic/__init__.py`, `streams.py`, `hooks.py`, `mcp.py`) is a thin layer on top: it drives `entropic_run_streaming` with a `TOKEN_CB` trampoline rather than the blocking `entropic_run`, and it wraps Python callables as `HOOK_CB` closures (`hooks.py:_build_trampoline`) that ctypes turns into real C function pointers the engine can call back into.

So: Python → ctypes → flat C ABI → the C++ engine sitting behind opaque handles. No C++ symbols, exceptions, or STL types ever cross; only ints, `char*`, `void*`, and C structs/enums do, exactly as `entropic.h`'s design rules mandate.

## The memory rules crossing that boundary

The header states the contract explicitly (`entropic.h:32-37`) and the Python side follows it:

- **Engine-allocated, caller-freed**: any function returning ownership of a `char*` (e.g. `entropic_run`'s `result_json`, `entropic_context_get`, `entropic_metrics_json`, `entropic_list_mcp_servers`, `entropic_residency_snapshot`) transfers a heap pointer to the caller, who **must** free it with `entropic_free()` — never Python's own allocator, never `libc free()` directly, since the engine may use a different allocator internally.
- **Caller-allocated, engine-freed — and it must go through `entropic_alloc`**: for the reverse direction (data Python hands the engine that the engine will later free), the header is explicit: *"Consumers providing buffers the engine will free (e.g., hook `modified_json`) MUST allocate with `entropic_alloc()`."* `entropic/hooks.py` implements exactly this: `_alloc_c_string()` and the hook trampoline both call `entropic_alloc(len)` + `ctypes.memmove()` to copy a Python-produced string into engine-owned memory before handing the pointer back across the boundary — allocating with Python's own memory (e.g. via `ctypes.create_string_buffer`, which the engine cannot free) would be a mismatched-allocator free and undefined behavior.
- **`const char*` returns are borrowed, not owned**: strings like `entropic_version()` or callback-scoped strings (`tier_name`, `model_path`, hook `context_json`, delegation request/result fields) are "owned by the handle" or "valid only for the callback's duration" — Python must copy out what it needs (`ctypes.string_at(...).decode("utf-8")`, as seen in `hooks.py` and `helpers.py:30`) before returning from the callback or making another call on the handle, because a next call can invalidate the pointer.
- **Callbacks must not re-enter the engine**: `entropic_run_streaming`'s `on_token` doc says the callback "must not call back into the entropic API (deadlock risk)" — this is a correctness rule about the C++ side's per-handle mutex, not memory per se, but it bounds what Python trampolines are allowed to do while inside a C callback frame.
- **Exceptions never cross**: Python callback trampolines (`hooks.py:_trampoline`) wrap the user function in `try/except` and swallow any Python exception (logging via `traceback.print_exc()`, returning an int status code) rather than letting it propagate — an unhandled Python exception inside a `ctypes` callback would otherwise unwind into C++ stack frames with undefined results, consistent with the architecture rule "exceptions do not cross `.so` boundaries — error codes + callbacks."
- **Structs are POD mirrors, not owning types**: `EntDelegationResult`, `EntropicLogprobResult`, etc. are `ctypes.Structure`s whose pointer/array fields (`files_touched`, `logprobs`) point into engine memory; there's a dedicated `entropic_free_logprob_result()` to release the nested allocations in `EntropicLogprobResult`, since a bare `entropic_free()` on the struct pointer wouldn't reach its internal buffers.

In short: ownership crosses the boundary explicitly and asymmetrically per allocator — `entropic_alloc`/`entropic_free` is the *only* pair used for anything that moves ownership either direction — and everything else (`const char*`, callback-scoped struct fields) is borrowed and must be copied out before it can be assumed to survive.
