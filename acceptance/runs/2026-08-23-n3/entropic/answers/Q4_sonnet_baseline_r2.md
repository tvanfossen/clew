## Threads other than the caller's in entropic

Entropic spawns background threads in three purposes — an MCP client-server accept loop, async task execution, and int*↔atomic cancel bridging — plus one long-running background health monitor. The safety model is consistent throughout: **atomics for anything read/written from both sides without a lock, mutexes (or mutex+condvar) only around the specific state that genuinely needs serialization, and join-before-teardown for every spawned thread.** The documented policy backing this (`docs/architecture-cpp.md` decision #10) is literally "atomic state, mutex transitions — state queries are lock-free, only state changes take locks," and it's followed almost everywhere.

**MCP server side (`src/facade/external_bridge.cpp`)**
- `ExternalBridge::start()` spawns an accept thread that polls the Unix-socket listen fd. Shutdown is ordered explicitly: flip `std::atomic<bool> running_`, close the listen fd (which unblocks the accept/read calls), then join — no condvar needed because closing the fd itself wakes the blocked syscall.
- Each accepted connection gets its own `serve_client()` thread, tracked in `std::vector<std::unique_ptr<ClientThread>> client_threads_` under `client_threads_mutex_`. Each `ClientThread` carries its own `std::atomic<bool> finished` so the accept thread can reap dead workers without touching the vector under a stale assumption.
- `run_async_ask()` runs `entropic.ask{async:true}` on its own thread and updates a `tasks_` map under `tasks_mutex_`. A generation counter (`observer_gen_`) guards against a stale phase-observer callback mutating state after the task it belonged to was already cleared — a classic cross-thread callback race, closed by versioning instead of extra locking.

**Cancel bridging (`response_generator.cpp`, `interface_factory.cpp`, `inference_c_api.cpp`)** — three independent implementations of the same idiom: the C ABI can only carry `int*` across the `.so` boundary (no `std::atomic&` allowed there, per design rule #6 in the architecture doc: "exceptions/complex types don't cross `.so` boundaries"), so a short-lived poller thread bridges `int* cancel_flag` (written by the caller/UI thread) into an internal `std::atomic<bool>` the generation loop actually checks every ~10ms. Each of these threads is joined before the enclosing call returns, so the atomic never outlives its scope.

**Background health monitor (`src/mcp/health_monitor.cpp`)** polls watched external MCP servers on its own thread, guarded by `watched_mutex_` for the watch list and `event_mutex_` for an event queue. Critically, it never invokes the user's `status_callback_` directly from the background thread — it posts to `event_queue_`, and the engine's own thread drains it via `process_events()`. That's the "no cross-thread callback" rule stated in the header, and it sidesteps the whole class of bugs where a user callback isn't thread-safe.

**Transport readers (`transport_stdio.cpp`, `transport_sse.cpp`)** each run a background reader thread (stderr forwarding, SSE event parsing). The SSE case is the one spot with real producer/consumer coordination: the reader thread inserts into `pending_responses_` under `pending_mutex_` and calls `notify_all()`; the caller thread `wait_until`s on `pending_cv_` for its request ID to show up. `close()` also notifies the condvar so a caller blocked mid-wait doesn't hang when the transport tears down.

**The one deliberately unlocked cross-thread contract** is `EngineHandle::api_mutex` (`src/facade/engine_handle.h`) — every C-ABI entry point takes it *except* `entropic_run`/`entropic_run_streaming`/`entropic_run_with_cancel`, per gh#109: a long-running turn must not block `entropic_interrupt()` called from another thread. Safety there rests entirely on `interrupt_flag_`, `pause_flag_`, and `running_flag_` being atomics rather than on mutual exclusion — an explicit, documented trade of lock-safety for responsiveness.

**Net picture:** nothing in entropic shares mutable state across threads without either an atomic flag (for simple booleans/state enums/counters) or a mutex scoped tightly to the mutating operation (never to steady-state reads). Every spawned thread is joined by the object that owns it before that object finishes tearing down, and the one place where a lock is intentionally skipped (`entropic_run`) is called out by issue number in a comment rather than left implicit. That combination — atomic-for-read, mutex-for-transition, event-queue-for-callbacks, join-on-destruct — is applied identically across five independent subsystems (MCP bridge, health monitor, two transports, three cancel bridges), so it reads as an actual house style rather than one-off code.
