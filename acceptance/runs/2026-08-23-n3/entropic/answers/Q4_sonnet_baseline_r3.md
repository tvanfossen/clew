## Where entropic actually leaves the caller's thread

Nine sites, three shapes.

**1. The external MCP bridge is fully multithreaded (`src/facade/external_bridge.cpp`).**
- `start()` (`:796`) spawns a persistent accept-loop thread that polls the listening unix socket, validates peer UID, and for each connection spawns a *further* per-client serve thread (`:945`) that reads JSON-RPC lines and dispatches them into the engine.
- `run_async_ask()` (`:1158`) spawns a one-shot worker per `entropic.ask` call that runs the model, updates task state, and broadcasts progress notifications.

What keeps it safe: `running_` (`std::atomic<bool>`) is the lock-free stop signal every loop polls; `client_threads_mutex_` guards the client-thread registry; `tasks_mutex_` guards the task map and is explicitly documented as needing to cover the terminal-state write *and* the sentinel-file write before the MCP notification fires, so an observer can never see a notification without matching persisted state. A generation counter (`observer_gen_` / `attached_gen_`) protects against a stale progress callback firing after `detach_phase_observer()` — a classic use-after-detach race — by making staleness detectable rather than preventing the race outright. The header's own "Thread safety" note says the engine handle's `api_mutex` is what ultimately serializes concurrent calls into the engine itself; the bridge threads just feed it.

**2. Cancel-flag poller threads — the same pattern implemented three times** (`response_generator.cpp:410`, `interface_factory.cpp:246`, `inference_c_api.cpp:385`). Each spins up a thread that busy-polls a foreign `int*` cancel signal every 10ms and mirrors it into a local `std::atomic<bool>`, because the C ABI boundary can't pass an atomic across the `.so` edge. Safety here is deliberately minimal: no mutex at all — the caller thread always `join()`s the poller before touching anything the poller captured, so lifetime is join-serialized rather than lock-protected.

**3. Long-lived background readers** — `HealthMonitor::monitor_loop` (`health_monitor.cpp:92`), the stdio transport's `stderr_reader_loop` (`transport_stdio.cpp:164`), and the SSE transport's `sse_reader_loop` (`transport_sse.cpp:107`). Each posts results into a queue or map the caller drains, rather than calling back directly from the background thread:
- Health monitor: `watched_mutex_` + `event_mutex_` guard the watch list and event queue; a `condition_variable` (`wake_cv_`) lets `watch()`/`stop()` wake the loop early. Its header states the rule outright: *"status changes are posted to a thread-safe event queue... No cross-thread mutation of engine state."* The `status_callback_` only ever fires from `process_events()`, on the engine's own thread.
- SSE transport: `pending_mutex_` + `pending_cv_` implement the classic wait/notify handoff — the reader thread stashes a response keyed by request id and notifies; `send_request()` blocks on the CV with a deadline.

**The governing rule underneath all of it** is the inference backend's state machine (`include/entropic/inference/backend.h:10-16`, mirrored in `i_inference_backend.h` and `docs/architecture-cpp.md` rules #10/#11): `state_` is `std::atomic<ModelState>` for lock-free queries; `transition_mutex_` is taken only by `load/activate/deactivate/unload`; `generate*` deliberately does **not** take that mutex, so generation runs concurrently with state queries but never concurrently with a lifecycle transition; a separate `eval_mutex_` keeps `evaluate_logprobs` from blocking on generation. This is the "atomic for queries, mutex for transitions" rule your CLAUDE.md references, and it's also why `mtp_mutex_` (decision #43 in the architecture doc) exists — to serialize `generate_mtp` against `deactivate/unload` teardown without letting the mutex be re-entered from the already-locked setup path.

Net picture: everything that crosses a thread boundary here either (a) hands off through an atomic flag with join-based lifetime, (b) posts into a mutex/CV-guarded queue that only the owning thread drains, or (c) is fenced by the backend's atomic-state/mutex-transition split. Nothing found relies on a bare shared variable without one of those three patterns.
