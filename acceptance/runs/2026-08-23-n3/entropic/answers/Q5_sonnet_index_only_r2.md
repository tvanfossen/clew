## How Python actually reaches the engine

There's no C++ code linked directly into Python — the boundary is a pure C ABI, and Python reaches it two different ways depending on which entry point you use:

**1. CLI usage → `execvp`, not a call at all.** `python/src/entropic/cli.py` dispatches the `entropic` console script. For every subcommand except `install-engine`, it does `os.execvp` into the bundled native binary (`bin/entropic`, built from `src/cli/main.cpp`) and replaces the Python process outright — argv passes through verbatim, and the native C++ binary's own `print_usage()` becomes the real help text (the wrapper has no help text of its own). So for the CLI path, Python is just a launcher; nothing crosses in-process.

**2. Programmatic usage → ctypes over the C ABI.** `python/src/entropic/_bindings.py` is an auto-generated ctypes shim (generator: `scripts/gen_bindings.py`, driven off `include/entropic/entropic.h`) that exposes every `ENTROPIC_EXPORT` function, struct, enum, and callback typedef declared in the public facade. `_bindings_manifest.py` populates a lazy-export set at `entropic.__init__` import time *without* touching `librentropic.so`; the actual `ctypes.CDLL` load is deferred to `_loader.py`, which searches a fixed set of install paths (bundled path, `~/.entropic/entropic/lib/librentropic.so`, `~/.entropic/lib/librentropic.so` flat-form fallback, etc.) for the shared library that `entropic install-engine` fetches separately (downloads a cpu/cuda tarball from GitHub Releases based on an `nvidia-smi` probe). The Python wheel itself (~50 KB) ships **no native code at all** — the engine binary is a separate, on-demand download, so wrapper version and binary version can drift (an open issue noted in `docs/cli-install-routes.md`).

Everything the ctypes layer touches is declared "pure C — no C++ types cross this boundary" per `entropic.h`'s file doc, enforced by an opaque handle: `entropic_handle_t` is a pointer to `struct entropic_engine`, never exposed by value or by C++ type.

## Memory rules across the boundary

- **Handle lifecycle is create/destroy, one-to-one.** `entropic_create` heap-allocates the engine (`new (std::nothrow) entropic_engine()`) and hands back an opaque handle. `entropic_destroy` tears down subsystems in *reverse* creation order, is null-safe, and `delete`s the struct. After that call the handle is dead — nothing in the index suggests reference counting; ownership is single-owner, caller-destroys-exactly-once.

- **Engine-allocated memory must be freed through the engine, not by the Python side directly.** `entropic_alloc`/`entropic_free` are an explicit symmetric pair (`malloc`/`free` under the hood, but that's a private implementation detail, not a contract you're supposed to rely on) — anything the engine hands back through this path must come back through `entropic_free`, not through Python deciding to free it some other way.

- **Mixed ownership is called out explicitly where it exists.** `entropic_free_logprob_result` frees only the *internal arrays* of a `entropic_logprob_result_t` (`logprobs`, `tokens`) and nulls those pointers to prevent double-free — but its own doc comment states "the struct itself is caller-owned." That's a real trap for ctypes code: call the engine's free function to release the engine-owned interior, but the ctypes struct memory itself is managed by ordinary Python/ctypes rules.

- **Callback trampolines must be kept alive on the Python side, or the engine ends up holding a dangling function pointer.** `helpers.py`'s file doc spells this out directly: a `ctypes.CFUNCTYPE` instance (e.g. `_CB = DELEGATION_COMPLETE_CB(on_complete)`) has to be held in a Python variable "for the engine's lifetime — Python would otherwise garbage-collect the trampoline." `tests/unit/test_pythonic_facade.py`'s doc confirms the pattern in the actual facade code: a per-handle dict binds pending callback entries to a handle specifically to keep trampolines alive as long as the C side might invoke them. This is the sharpest of the memory rules because getting it wrong doesn't throw in Python — it corrupts state or crashes on the C side when the engine calls through a pointer whose backing Python object is already gone.

- **Callback-delivered pointers are borrowed, not owned, and only for the call's duration.** `include/entropic/interfaces/i_inference_backend.h`'s file doc states the `on_token` callback's pointer is "valid only for the callback duration. Caller must copy if they [need it longer]" — the same borrow-and-copy discipline the index shows applies generally at C-callback boundaries in this codebase, not just token streaming.
