Confirmed — every mutex-lock/unlock call site across the library is individually wrapped in `#if defined(MBEDTLS_THREADING_C)`, and `MBEDTLS_THREADING_C` is commented out in `include/mbedtls/mbedtls_config.h:3787`. That's the whole answer, so here it is straight:

**Nothing runs concurrently, by mbedtls's own design, and nothing is protected.**

mbedtls doesn't spawn threads itself — it's a library called into by an application. The threading layer (`library/threading.c`, `include/mbedtls/threading.h`) exists purely to let a multi-threaded *caller* register mutex hooks (`mbedtls_mutex_init/lock/unlock/free` as function pointers) so the library can guard its own shared state. That layer is gated behind `MBEDTLS_THREADING_C`, which is **off by default**. Two consequences of that:

1. `library/threading.c` is wrapped end-to-end in `#if defined(MBEDTLS_THREADING_C)` — in a default build the file compiles to nothing, and the mutex function-pointer declarations in `threading.h` (lines 105–161) don't even exist as symbols.
2. Every call site that would take a lock — in `psa_crypto.c`, `psa_crypto_random.c`, `psa_crypto_slot_management.c`, `entropy.c`, `ctr_drbg.c`, `hmac_drbg.c`, `rsa.c`, `x509_crt.c`, `ssl_cache.c`, `ssl_cookie.c`, `ssl_ticket.c`, `memory_buffer_alloc.c`, `platform_util.c` — is individually wrapped in the same `#if defined(MBEDTLS_THREADING_C)`. So it's not that locking degrades to a no-op; the locking code is stripped from the binary entirely.

What that protects *when enabled* (i.e., what's actually shared/racy if you do run this multithreaded without turning threading on): the PSA subsystem's implicit global state — key-slot table, global init data, RNG data (`mbedtls_threading_psa_globaldata_mutex`, `mbedtls_threading_key_slot_mutex`, `mbedtls_threading_psa_rngdata_mutex` in `psa_crypto.c`), RSA blinding parameters, the `mbedtls_x509_crt` cache lookups, `ssl_cache`/`ssl_cookie`/`ssl_ticket` server-side session stores, and the optional `memory_buffer_alloc` heap replacement.

The config comment (`mbedtls_config.h:3744–3773`) spells out the assumption directly: *"Traditionally, Mbed TLS assumes it is used in a non-threaded environment or that contexts are not shared between threads."* Default config = single-threaded assumption, full stop. If an application spins up its own threads and shares any mbedtls or PSA context across them without flipping on `MBEDTLS_THREADING_C` + either `MBEDTLS_THREADING_PTHREAD` (POSIX `pthread_mutex_t`, implemented in `threading.c`) or `MBEDTLS_THREADING_ALT` (caller-supplied hooks), that's a data race the library will not catch or prevent — the mutex code to prevent it is compiled out, not merely idle.
