Everywhere in the library that needs heap memory calls exactly two functions, `mbedtls_calloc()` and `mbedtls_free()` — nothing in the ~360 call sites (bignum, ASN.1, PK, cipher, RSA, PSA crypto, etc.) ever calls `malloc`/`calloc`/`free` directly. What those two names actually resolve to is decided entirely in `include/mbedtls/platform.h`, in a small compile-time decision tree:

- **`MBEDTLS_PLATFORM_MEMORY` off (the default):** `platform.h` just `#define`s `mbedtls_calloc calloc` and `mbedtls_free free` — you get the libc allocator, and the layer is otherwise inert.
- **`MBEDTLS_PLATFORM_MEMORY` on, with `MBEDTLS_PLATFORM_CALLOC_MACRO`/`FREE_MACRO` also defined:** the names are `#define`d directly to your macros at compile time (`platform.h:143-144`); no indirection, no function pointer, this is baked into the binary.
- **`MBEDTLS_PLATFORM_MEMORY` on without those macros:** `mbedtls_calloc`/`mbedtls_free` become real functions defined in `library/platform.c`, which are thin wrappers that call through two static function pointers, `mbedtls_calloc_func`/`mbedtls_free_func` (`platform.c:44-53`). Those pointers default to `MBEDTLS_PLATFORM_STD_CALLOC`/`STD_FREE` (themselves `calloc`/`free` unless you've overridden those too, or a stub that always fails/no-ops if you defined `MBEDTLS_PLATFORM_NO_STD_FUNCTIONS`), and a project can repoint them at runtime with `mbedtls_platform_set_calloc_free(my_calloc, my_free)` (`platform.c:56-62`, declared in `platform.h:160`).

So substitution is either compile-time (macro override — zero overhead, fixed for the life of the binary) or run-time (function-pointer swap via `mbedtls_platform_set_calloc_free`, useful when you want to change/reset the allocator per test or per boot, e.g. embedded targets picking a pool allocator once RTOS heap is up). Both paths require `MBEDTLS_PLATFORM_C` and `MBEDTLS_PLATFORM_MEMORY` enabled in `mbedtls_config.h`; the full decision tree is spelled out in the doc comment at `mbedtls_config.h:172-195`.

As for what mbedtls itself does with this facility beyond providing the seam: it ships one concrete alternative allocator, `library/memory_buffer_alloc.c` (`memory_buffer_alloc.h`) — a buffer/pool-based allocator over a caller-supplied static buffer, with alignment control (`MBEDTLS_MEMORY_ALIGN_MULTIPLE`) and optional debug/verification modes (`MBEDTLS_MEMORY_VERIFY_ALLOC`/`FREE`). Its own init function calls `mbedtls_platform_set_calloc_free()` to install itself as the global allocator — this is the mechanism intended for heap-less embedded targets or for buffer-overflow/allocator-abuse testing, not something wired into the TLS/crypto code paths themselves. Everywhere else, the library is allocator-agnostic: it just calls `mbedtls_calloc`/`mbedtls_free` and trusts whatever's behind them.
