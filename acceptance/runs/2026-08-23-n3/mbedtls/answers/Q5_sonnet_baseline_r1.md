## The mechanism: it's not a compiler guarantee, it's a hand-built abstraction layer

mbedtls's "constant time" code isn't `constexpr`-style enforcement — there's no compiler flag that verifies it. It's a small header/source pair, `library/constant_time_internal.h` + `library/constant_time_impl.h` + `library/constant_time.c`, that provides an opaque type (`mbedtls_ct_condition_t`) and a fixed set of primitive operations (`mbedtls_ct_bool`, `mbedtls_ct_uint_lt/eq/ne`, `mbedtls_ct_if`, `mbedtls_ct_memcmp`, `mbedtls_ct_memcpy_if`, etc.). Code that needs to branch on secret data is written entirely in terms of these primitives instead of `if`/`?:`/`==` on secret values — so the *source itself* has no data-dependent control flow to secret-dependent branches; that's the actual enforcement mechanism, at the level of engineering discipline, not the CPU.

The instruction-level part is inside those primitives. For four architecture families — ARM32/Thumb, AArch64, x86, x86-64 — each primitive has a hand-written GNU inline-asm implementation using only unconditional bitwise/arithmetic instructions (`neg`, `orr/or`, `asr/sar`, `and`, `bic`/`not`, `eor/xor`) — no `cmp`+`jcc`, no `cmov`, no `csel`. E.g. `mbedtls_ct_bool` on x86-64:

```asm
mov %x,%s ; neg %s ; or %s,%x ; sar $63,%s
```

turns "is x nonzero" into an all-ones/all-zeros mask via sign propagation, entirely branch-free at the machine-instruction level. `mbedtls_ct_if(cond, if1, if0)` becomes `(cond & if1) | (~cond & if0)` in registers. The `asm volatile` blocks also serve a second purpose: they're opaque to the optimizer, so it cannot see through the mask math, decide "this is just a select," and reintroduce a `cmovcc` or branch during instruction selection — which compilers have been observed doing to *pure C* boolean-mask idioms.

## What happens on a compiler/architecture that can't do this

`MBEDTLS_CT_ASM` is only defined when `MBEDTLS_HAVE_ASM` is set, GNU extended asm is available, and the arch matches one of the four families (`constant_time_impl.h:40-51`). Everywhere else — other architectures, or GNU asm disabled — every primitive falls back to a **plain C path** guarded by `#else`. That fallback still tries to be constant-time by construction (sign-bit extraction via unsigned/signed casts and shifts, XOR-based inequality, no comparison operators — the file comment says explicitly "implemented without using comparison operators, as those might be translated to branches by some compilers"), but it has no hard guarantee. The one thing it does add is `mbedtls_ct_compiler_opaque()`: XOR-ing against an `extern volatile mbedtls_ct_uint_t mbedtls_ct_zero` (defined in `constant_time.c`, always zero) so the compiler can't prove the value at compile time and constant-fold or branch on it.

So the degradation path is: known asm arch → hand-verified branch-free instructions; unknown compiler/arch → best-effort C idiom that has been *empirically observed* (per the header's comment, "as of May 2023") to compile branch-free under current gcc/clang/MSVC, backed by a volatile-opacity trick, but with no formal guarantee. `SECURITY.md` states this residual risk explicitly rather than pretending it's solved: "given the diversity of compilers, compiler options and target platforms, this prevention may not be complete," recommending `-O2`/`-Os`, treating side channels under common compilers/optimization levels as vulnerabilities, but not promising safety at `-O3`/`-Oz` or with arbitrary flags.

## How far it reaches

It's not confined to bignum/RSA. Grepping `mbedtls_ct_` call sites across `library/` turns up: `bignum.c`/`bignum_core.c`/`bignum_mod_raw.c` (MPI comparisons, conditional selects — the modexp/ECC substrate), `rsa.c` (PKCS#1 v1.5 unpadding — the classic Bleichenbacher-oracle surface, using `mbedtls_ct_error_if`, `mbedtls_ct_zeroize_if`, `mbedtls_ct_memmove_left`), `ssl_msg.c`/`ssl_tls.c`/`ssl_tls12_client.c`/`ssl_tls12_server.c`/`ssl_tls13_generic.c`/`ssl_tls13_server.c` (CBC MAC/padding checks in the TLS record layer — the Lucky-13 surface, including a constant-time HMAC `mbedtls_ct_hmac`), `cipher.c`, `cmac.c`, `ccm.c`, `gcm.c`, `chachapoly.c`, `nist_kw.c`, `base64.c`, `ssl_cookie.c`, and `psa_crypto.c`/`psa_crypto_cipher.c`/`psa_crypto_mac.c` (the PSA crypto layer). So it spans low-level bignum arithmetic, RSA padding, symmetric AEAD/MAC verification, the TLS record-processing hot path across both TLS 1.2 and 1.3 code, and the PSA API surface — everywhere a secret-dependent comparison or branch would otherwise leak timing.

It's explicitly *not* a blanket guarantee across the library, though. `SECURITY.md` calls out the pure-software block-cipher implementations (AES/Camellia/ARIA/DES) as using table lookups that remain timing-vulnerable regardless of this facility, recommending hardware acceleration (`MBEDTLS_AESCE_C`/`MBEDTLS_AESNI_C`/`MBEDTLS_PADLOCK_C`) or non-block-cipher alternatives (ChaCha20-Poly1305, HMAC_DRBG) as the actual mitigation there — the `mbedtls_ct_*` layer doesn't cover table-lookup-induced cache-timing side channels at all, only explicit branch/compare elimination.
