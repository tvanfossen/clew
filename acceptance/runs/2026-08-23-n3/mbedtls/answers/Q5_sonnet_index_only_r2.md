## How mbedtls enforces constant time at the instruction level

The whole facility sits in three files: `include/mbedtls/constant_time.h` (public API), `library/constant_time_internal.h` (the `mbedtls_ct_condition_t`/`mbedtls_ct_uint_t` types and `MBEDTLS_CT_TRUE`/`FALSE`), and `library/constant_time_impl.h` (the actual branchless primitives — comparisons, selects, boolean algebra over `mbedtls_ct_condition_t`).

The core trick is that a "condition" isn't a `bool` you branch on — it's an all-bits-set or all-bits-clear mask (`MBEDTLS_CT_TRUE = compiler_opaque(SIZE_MAX)`, `MBEDTLS_CT_FALSE = compiler_opaque(0)`), and every higher-level operation (`mbedtls_ct_uint_if`, `mbedtls_ct_bool_and/or/not`, `mbedtls_ct_memcpy_if`, `mbedtls_ct_zeroize_if`, …) is built by ANDing/ORing that mask against data rather than testing it in an `if`.

Where the project doesn't trust the compiler to keep that promise, it drops to **inline GCC-style asm** (`asm volatile`) for the primitive mask-generating operations (`mbedtls_ct_bool`, `mbedtls_ct_uint_lt`, `mbedtls_ct_compiler_opaque`, etc.), with a hand-written variant per architecture:

- **AArch64** (`MBEDTLS_CT_AARCH64_ASM`): `neg`/`orr`/`asr` (for `bool`) or `eor`/`sub`/`bic`/`and`/`orr`/`asr` (for `lt`) — no branch, no `cmp`+conditional-branch, no data-dependent instruction at all.
- **32-bit ARM** (`MBEDTLS_CT_ARM_ASM`): the Thumb/ARM equivalent (`negs`/`orrs`/`asrs`, `.syntax unified`, with `RESTORE_ASM_SYNTAX` cleanup and explicit `"cc"` clobber since these forms touch flags).
- **x86-64** (`MBEDTLS_CT_X86_64_ASM`): `mov`/`neg`/`or`/`sar` for `bool`, `mov`/`xor`/`sub`/`and`/`not`/`and`/`or`/`sar` for `lt`.
- **x86 (32-bit)** (`MBEDTLS_CT_X86_ASM`): the same shape with 32-bit registers.

`mbedtls_ct_compiler_opaque` — the value-hiding primitive everything else calls — is itself a single `asm volatile ("" : [x] "+r" (x) :)`: an empty asm block that forces the compiler to materialize `x` in a register and treat it as unknown afterward, purely to defeat constant propagation/value-range analysis. This is the actual "instruction level" enforcement: hand-picked instruction sequences, in a register-constrained asm block, chosen because they have no data-dependent branch, no data-dependent memory access pattern, and (for the arithmetic forms) no operation whose *latency* varies with the operand value on the target ISA.

Whether any of this is compiled in at all is gated by three preprocessor conditions on `MBEDTLS_CT_ASM` (visible in the index's `gated_by`): `MBEDTLS_HAVE_ASM && (__GNUC__ || __ARMCC_VERSION)`, further split into per-arch variants keyed on `MBEDTLS_CT_SIZE_32`/`MBEDTLS_CT_SIZE_64`.

## What happens when the compiler can't take the asm path

Every one of these functions is written as `#if <asm variant> ... #elif <next arch> ... #else <plain C fallback> #endif`. If asm support isn't detected — `MBEDTLS_HAVE_ASM` unset, a non-GCC/non-ARMCC compiler (e.g. MSVC), or an architecture with none of the four hand-written variants — the code falls through to a **plain-C fallback** that tries to achieve the same branchless property through arithmetic/bitwise tricks instead of literal instruction selection. For example, `mbedtls_ct_bool`'s fallback computes `y = (-xo) | -(xo >> 1)`, shifts out the sign bit, and negates it to get an all-ones/all-zeros mask — no `if`, but also no instruction-level guarantee, just reliance on the compiler not turning subtraction/shift/negation into a conditional move or branch.

The source comment on that fallback path is explicit about the honesty of this: it says the plain-C form "does not get optimised into conditional instructions or branches by trunk clang, gcc, or MSVC (as of May 2023)" — i.e. it is empirically verified against specific compiler versions at a point in time, not a language-level guarantee. `mbedtls_ct_compiler_opaque` has the identical shape: asm barrier when available, otherwise `return x ^ mbedtls_ct_zero` (a global volatile-ish zero) as a much weaker, best-effort attempt to stop constant folding. So the honest answer to "what happens on an unsupported compiler" is: **the code still runs correctly, but the constant-time property degrades from an instruction-level guarantee to an optimizer-behavior assumption** that the project has checked empirically rather than proven. There's no third path that refuses to build or forces something else — it silently falls back.

Two more mechanisms in `constant_time.c` reinforce this at the memory-access level rather than the ALU level: `mbedtls_ct_memcmp` casts its input pointers to `volatile` specifically to stop the compiler from short-circuiting the comparison loop once `diff` is fully set, and `mbedtls_ct_memcpy_if`/`mbedtls_ct_zeroize_if` always touch every byte of both `src1` and `src2` (masking and OR-ing) rather than choosing which buffer to read, so the memory access *pattern* doesn't depend on the secret condition either — this matters for cache-timing side channels, which pure branchless-ALU code doesn't address by itself.

## How far it reaches into the library

This isn't a niche utility — the index shows it wired directly into the security-sensitive comparison/selection points across several subsystems:

- **Bignum / RSA core math**: `mbedtls_mpi_lt_mpi_ct` (`library/bignum.c`) composes `mbedtls_ct_bool`, `mbedtls_ct_bool_and/or/not`, `mbedtls_ct_uint_if_else_0`, and `mbedtls_mpi_core_lt_ct` to compare signed MPIs without branching on sign or magnitude — used for constant-time modular arithmetic paths. `mbedtls_mpi_core_check_zero_ct` and `mbedtls_mpi_core_lt_ct` (`bignum_core.h`) and `mbedtls_mpi_gcd_modinv_odd` (`bignum_internal.h`) are the lower-level constant-time primitives those build on.
- **RSA PKCS#1 v1.5 decryption**: `mbedtls_ct_rsaes_pkcs1_v15_unpadding` (`library/rsa.c`) is the textbook Bleichenbacher-oracle defense — its own comment explicitly states the sensitive variables "must not leak into observable behavior... otherwise this would open the execution... to side-channel-based variants of the Bleichenbacher padding oracle attack." It uses `mbedtls_ct_bool`, `mbedtls_ct_uint_ne/eq/gt`, `mbedtls_ct_uint_if`, `mbedtls_ct_error_if`, `mbedtls_ct_zeroize_if`, and `mbedtls_ct_memmove_left` to decode padding, compute plaintext length, and relocate the plaintext with a memory-access trace independent of padding validity or length.
- **TLS record layer**: `mbedtls_ct_hmac` in `library/ssl_msg.c` — the CBC MAC-then-encrypt padding-oracle defense (the TLS analogue of the RSA case above).
- **Base64**: `mbedtls_ct_base64_dec_value` / `mbedtls_ct_base64_enc_char` in `library/base64.c` — constant-time table lookups so the base64 alphabet position doesn't leak through timing.
- **Generic helpers used everywhere**: `mbedtls_ct_memcmp` (buffer equality — the public, most widely reusable primitive), `mbedtls_ct_memcpy_if`/`mbedtls_ct_memcpy_offset`/`mbedtls_ct_memmove_left`, `mbedtls_ct_zeroize_if`.

So the facility isn't confined to one algorithm — it's the shared branchless-arithmetic toolkit underneath RSA padding, bignum comparison/GCD, TLS MAC verification, and base64, anywhere the project has identified a secret-dependent branch or memory-access pattern as a side-channel risk. The index's call graph is doxygen/AST-resolved by name, so for very generic helper names (`mbedtls_ct_bool`, `mbedtls_ct_if`) there's some risk of over-collapsing distinct call sites — but the specific chains shown above (RSA unpadding → zeroize/memmove, `mpi_lt_mpi_ct` → bool/if primitives) are concrete, resolved edges, not just name matches.

One thing the index can't tell you: whether test coverage specifically exercises the "no asm available" fallback path (e.g. via CI on MSVC or a forced `#undef MBEDTLS_CT_ASM`) — `covering_tests` came back empty for all the functions I checked, which may mean the query surface doesn't map dg_source-tagged tests onto this file, or may mean there genuinely isn't dedicated coverage. That's a source-reading question the index can point at but not settle.
