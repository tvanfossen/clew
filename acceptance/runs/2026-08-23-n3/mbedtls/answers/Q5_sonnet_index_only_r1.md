Now I have the whole picture, grounded directly in the index. Here's how it works.

## The mechanism: hand-written asm branch-free primitives, with a portable bitwise fallback

The facility lives in three files that the index treats as the root of this subsystem: `include/mbedtls/constant_time.h` (public API), `library/constant_time_impl.h` (the branch-free primitive implementations, inlined into every translation unit that includes it), and `library/constant_time_internal.h` (the `mbedtls_ct_condition_t`/`MBEDTLS_CT_TRUE`/`MBEDTLS_CT_FALSE` type layer). There is no runtime "detect and enforce" — this is a compile-time-selected implementation, chosen by preprocessor gates, of the same handful of primitives: `mbedtls_ct_if` (select), `mbedtls_ct_uint_lt`/`_eq`/`_gt` (compare), `mbedtls_ct_bool_*` (boolean algebra over the opaque condition type), and `mbedtls_ct_compiler_opaque` (the value-hiding barrier everything else is built on).

Each primitive (`mbedtls_ct_if`, `mbedtls_ct_uint_lt`, …) is written as a chain of `#elif` blocks selecting between four *inline asm* implementations — AArch64, 32-bit ARM/Thumb, x86-64, x86 — each doing the select/compare with a fixed, unconditional sequence of `and`/`eor`/`sub`/`orr`/`asr` instructions with named-operand constraints, so there is no branch instruction the compiler could emit and no way for a data-dependent branch predictor or micro-op fusion path to leak timing. That's the literal instruction level: e.g. `mbedtls_ct_uint_lt`'s x86-64 path computes `x<y` via `xor`/`sub`/`and`/`not`/`and`/`or`/`sar $63` with `asm volatile` and explicit register constraints — no `cmp`+`jl`.

**What happens when the compiler can't support it:** the final `#else` arm of every one of these primitives is a plain-C bitwise fallback (mask-and-select via `(condition & if1) | (not_cond & if0)`, or a MSB-comparison trick for `<`). This path is taken when none of `MBEDTLS_CT_AARCH64_ASM` / `MBEDTLS_CT_ARM_ASM` / `MBEDTLS_CT_X86_64_ASM` / `MBEDTLS_CT_X86_ASM` are defined — i.e. no `MBEDTLS_HAVE_ASM` support, or a compiler other than GCC/Clang/ARMCC (the `MBEDTLS_CT_ASM` gate itself is keyed off `MBEDTLS_HAVE_ASM && (__GNUC__ || __ARMCC_VERSION)`, per `constant_time_impl.h:40`). This fallback isn't "best-effort" hand-waving — it depends entirely on `mbedtls_ct_compiler_opaque()`, which under `MBEDTLS_CT_ASM` is a zero-cost `asm volatile("" : "+r"(x) :)` optimization barrier, and under *no* asm support degrades further to `return x ^ mbedtls_ct_zero` (XOR with a value the compiler is trusted not to prove is zero). So on a compiler that can't do inline asm at all, mbedtls falls back to relying on the optimizer not folding a bitwise identity across a data flow it can't see through — a strictly weaker, "constant-time on a best-effort C-abstract-machine basis" guarantee rather than an instruction-level one. The comments in the source are explicit that this is exactly the boundary being managed.

## How far it reaches

This is not confined to one algorithm — it's the load-bearing plumbing under most of the side-channel-sensitive surface of the library, confirmed by caller edges in the index:

- **Bignum/MPI core** — `mbedtls_mpi_lt_mpi_ct`, `mbedtls_mpi_core_lt_ct`, `mbedtls_mpi_core_check_zero_ct`, and `mbedtls_ct_mpi_sign_if` (called from `mbedtls_mpi_safe_cond_assign`, `mbedtls_mpi_safe_cond_swap`, and `mbedtls_mpi_exp_mod_optionally_safe`) — this is what keeps modular exponentiation (RSA/DH) free of secret-dependent branches on the sign and magnitude of limbs.
- **RSA PKCS#1 v1.5 unpadding** (`mbedtls_ct_rsaes_pkcs1_v15_unpadding` in `rsa.c`) — the textbook Bleichenbacher-oracle defense, built entirely out of `mbedtls_ct_bool`/`mbedtls_ct_bool_or`/`mbedtls_ct_uint_eq` plus `mbedtls_ct_memmove_left`/`mbedtls_ct_zeroize_if`, with a comment in the body spelling out exactly the threat model (timing, cache access pattern, branch-predictor state).
- **TLS record MAC handling** (`mbedtls_ct_hmac` in `ssl_msg.c`) — implements the Lucky-13-style constant-flow HMAC-then-decrypt by cloning a PSA hash operation and processing every byte up to `max_data_len` regardless of the real (secret) length.
- **Base64 decoding** (`mbedtls_ct_base64_dec_value`, called from `mbedtls_base64_decode`) — avoids leaking which character class an input byte falls into, via `mbedtls_ct_uchar_in_range_if`.
- **Generic buffer comparison/copy** — `mbedtls_ct_memcmp` (volatile-qualified reads to defeat early-exit optimization) and `mbedtls_ct_memcpy_if` (branchless masked copy) are public API in `constant_time.h`, available for any consumer.

So the reach is: bignum/RSA at the arithmetic core, RSA padding at the protocol-attack level, TLS record processing, and a generic public utility layer (memcmp/memcpy/base64) that other parts of the library and even application code can call directly. The index's `also_in`/caller edges make this a first-party, structural fact rather than an inference from naming — it's the same `mbedtls_ct_*` primitive family threaded through all of it, not independent ad hoc implementations per subsystem.

One honest gap: the index resolves `MBEDTLS_HAVE_ASM`'s definition sites (default config, several `configs/*.h` profiles) but has no definition site for `__GNUC__`/`__ARMCC_VERSION` — expected, since those are compiler-predefined, not repo-defined, so I can't cite a row for them; that's consistent with the gate as written in `constant_time_impl.h:40`, not a hole in the mechanism.
